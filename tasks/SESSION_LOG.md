### Сделано

**§26 «Одна точка входа на контур».** У каждого контура ровно один файл с картой
раздела; новый файл называется в нём тем же коммитом; второго входа в тему

**Правда в документации.** README обещал SQL-представления в `sql/views/` —

**`docs/CRONS.md` описывал 13 заданий из 21.** Таблица собрана заново из `cron.job`.
Записано, что сверять состав заданий по именам файлов миграций нельзя: MCP
`apply_migration` присваивает свою метку времени, в `schema_migrations` 164 версии

живые акции. Состав участников не пришёл: WB отдаёт 422.

Разведка через `probe-wb-api` показала почему:

| запрос | ответ |
|---|---|
| `/calendar/promotions/details?promotionIDs=…` | 200 |
| `/nomenclatures?inAction=true` | 422 Unprocessable entity |
| `/nomenclatures?inAction=false` | 422 |
| `/nomenclatures` без `inAction` | 400 Invalid query params |

Метод состава для авто-акций закрыт, а все акции WB сейчас `type='auto'`.
Функция ходила туда и молча получала 422 на каждую акцию — таблица участников
пустовала не из-за бага, а потому что данных больше не отдают.

Взамен `/details` даёт агрегаты и **пороги бустинга**. Для «Бархатных скидок»

**Книги Excel.** По решению владелицы оставлена одна — `UNIT_economics_cogs_tariffs.xlsx`,

### Открытые задачи

**Деплой `fetch-wb-promotions` отклонён владелицей** — новая версия функции лежит
в ветке, но в проде работает старая. Пока не задеплоена, колонки участия
и `v_wb_promotions_boost` остаются пустыми. Cron акций тоже не включён:
включать его имеет смысл вместе с деплоем.

**`fetch-wb-supplies` — причина найдена, правка не написана.** Разведка через
`probe-wb-api` 04.09:

| запрос | ответ |
|---|---|
| `GET /api/v1/supplies` | 405 Method Not Allowed |
| `GET /api/v1/supplies?limit=10&next=0` | 405 |
| **`POST /api/v1/supplies` с телом `{limit, offset}`** | **200, данные пришли** |
| `POST /api/v1/supplies/list` | 405 |
| `GET /api/v1/warehouses` | 404 «This method is temporarily disabled», release-notes id=570 |
| `GET /api/v1/acceptance/coefficients` | 404 path not found |

**WB перевёл метод с GET на POST** — путь тот же, отсюда 405, а не 404: сервер

Правка не написана намеренно: менять функцию наспех в ночь смысла нет, к тому же
второй её запрос — `/api/v1/supplies/{id}/goods` — тоже нужно проверить, а деплой
накануне был отклонён. Работа на завтра, диагноз готов.

**Мусор в `wb_promotions`:** четыре записи `Excel TEST: Акция 1–4` с типом

**`yc-functions/`** — владелица ответила «не поняла», объяснение не дано,
решение не принято. В README каталога стоит пометка, что слой не используется.

## 2026-08-28 — Разрешения веб-сессий: четыре захода, три неверных диагноза

> Параллельная сессия в тот же день закрывала таблетницы и инфографику — её запись
> ниже. Здесь только инфраструктура: почему каждая сессия требовала ручных
> подтверждений и чем это кончилось. Работы по карточкам эта сессия не касалась,
> кроме собранного накануне материала по мячам.

### Контекст

Владелица: «постоянно приходится подтверждать твои действия». Список разрешений
в `AI_OS/.claude/web-permissions.json` существовал и содержал нужные инструменты,
но окна возвращались в каждой новой сессии. Разбор занял четыре захода; первые три
были неверными диагнозами, и каждый выглядел убедительно.

### Что оказалось верным

Нужны были **четыре условия одновременно**, и до этой сессии не выполнялось ни одно
из последних трёх:

1. Путь `$HOME/.claude/settings.json`. `HOME` в контейнере равен **`/root`**, а скрипт
   писал в `/home/user/.claude/settings.json` — это настройки уровня проекта для корня
   сессии, разрешения на MCP-инструменты из них не применяются.
2. `defaultMode: auto`. Стоявший `acceptEdits` пропускает без вопросов **только правки
   файлов**; вызовы инструментов подтверждаются даже будучи в `allow`.
3. Модель **4.6 или новее**. На Haiku 4.5 режим `auto` недоступен — серый в переключателе
   с пометкой «Requires Claude 4.6 or newer», сессия откатывается на `acceptEdits`.
4. Setup script в окружении, а не ручной запуск. Заведено новое окружение **`Arols`**:
   поле `Default` интерфейс редактировать не даёт.

### Три неверных диагноза — сохранены намеренно

| версия | почему неверна |
|---|---|
| Списка нет в `main` AI_OS | Был. Я проверял по устаревшему `origin/main`, не сделав `fetch` |
| Нужны копии `.claude/settings.json` по репозиториям | В веб-сессии не читаются: корень сессии `/home/user` и он не репозиторий. В SellerBase копия лежала с `execute_sql` внутри — и не работала |
| Режим `dontAsk` | Такого значения не существует. Допустимы `plan`, `ask`, `auto`, `bypassPermissions` |

Ещё одно наблюдение, стоившее времени: **прерывание вызова — не отказ в разрешении.**
Когда владелица пишет сообщение посреди работы, вызов отменяется и в логе выглядит
как «Denied by user». Дважды принял это за проблему с allowlist.

### Чем кончилось

Окна исчезли везде, **кроме вызовов MCP-коннекторов** вроде `Execute SQL (Supabase)`.
Это устройство площадки: `auto` — режим с классификатором, а не «разрешить всё», и запрос
к боевой базе он считает рискованным даже при `SELECT`. В окне только «Allow once»
и «Deny» — кнопки «разрешить всегда» для коннекторов не предусмотрено.

**Решение владелицы: так и оставить.** `bypassPermissions` убрал бы и это, но вместе
со всем списком `deny` — `rm -rf`, force-push, push в `main`, `reset --hard`, `curl`,
`wget`, секреты, `.env`. Защита от необратимого дороже нескольких подтверждений в день.
Подтверждать — **Ctrl+Enter**.

### Изменения в репозиториях

- `AI_OS` #121 — allowlist 86 → 106 записей, канон `docs/rules/core/web-permissions.md`
- `AI_OS` #122 — настоящая причина: корень сессии не репозиторий

**🟠 Найден баг веса.** `unit_weight_kg` пуст у **38 из 79** активных SKU, при том что
