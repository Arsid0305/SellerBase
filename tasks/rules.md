## 1. Тестовая неделя для любых изменений в финансовых формулах

**Правило:** при добавлении новой колонки / коэффициента / формулы в `wb_reports_fact` или производные сущности (комиссия, СПП, выручка по карточке, маржа, etc.):

1. Делаем миграцию + правим маппинг в edge function.
2. **Сначала перезаливаем ТОЛЬКО тестовую неделю `2025-12-01 — 2025-12-07`** (отчёты `559705441` Основной + `559705442` По выкупам).
3. Сверяем с цифрами владелицы из её WB-кабинета и Excel `PL WB (нед)` (колонка `01.12-07.12`).
4. **Только после совпадения** раскатываем перезалив на весь год (12 месяцев × 1-2 параллельно).

**Почему:** у владелицы по этой неделе есть и WB-скриншоты, и Excel-сверка, и наша БД-сверка. Это «золотая» точка калибровки. Если новая формула на ней не сходится — глобальный перезалив = трата ресурсов + засорение БД мусором.

**Эталонные цифры за 01.12–07.12.2025** (сумма отчётов `559705441` + `559705442`):

| Метрика | Значение | Источник | Формула |
|---|---:|---|---|
| Продажи шт (Excel R7) | 246 | Excel | `SUM(quantity)` Продажи |
| **Продано по цене в карточке (Excel R14)** | **170 768 ₽** | Excel + WB скрин | `SUM(retail_price × quantity)` Продажи **− Возвраты руб (R22)** |
| Выручка ВБ реализовал (Excel R15 / WB «Продажа») | 114 665 ₽ | Excel + WB | `SUM(retail_amount)` net (Продажи − Возвраты) |
| Комиссия ВБ (Excel R17) | 53 235 ₽ | Excel | `R14 − R20` (т.е. карточка минус к перечислению — НЕ классическая комиссия, а полное удержание ВБ) |
| % комиссии (Excel R18) | 31,17% | Excel | `R17 / R14` |
| К перечислению (Excel R20 / WB «К перечислению за товар») | 117 533 ₽ | Excel + WB | `SUM(ppvz_for_pay)` |
| Возвраты руб (Excel R22) | 628 ₽ | Excel | Sum возвратов по retail_price |
| Возвраты шт (Excel R23) | 1 | Excel + WB | `COUNT(*)` doc_type_name='Возврат' |
| Логистика (WB скрин) | 18 495,37 ₽ | WB скрин | `SUM(delivery_rub)` |
| Хранение (WB скрин) | 6 021,16 ₽ | WB скрин | `SUM(storage_fee)` |
| Компенсация СПП (WB скрин, только Основной) | 24,33 ₽ | WB скрин | |
| Итого к оплате (WB скрин) | 93 015,89 ₽ | WB скрин | |

**Важно про СПП:**
- `ppvz_spp_prc` в WB API — **средневзвешенный** процент скидки СПП на конкретный товар, обычно ~20–25%.
- Реальная скидка от карточки за неделю получается выше (32,9% для этой недели), потому что в R14 владелица **вычитает возвраты**, а ещё работает накопительная скидка покупателя.
- **Правильная формула «по карточке» = `SUM(retail_price × quantity) для Продаж − SUM(retail_amount) для Возвратов`**, НЕ `retail_amount × (1 + spp_prc/100)`.

## 2. Перезалив исторических данных в WB API

- WB Statistics API отдаёт полную детализацию (storage_fee, acquiring_fee, spp_prc и т.д.) за весь 2025 год.
- Edge function упирается в wall-clock таймаут при периодах > ~3 месяцев.
- **Рабочая стратегия:** месячные чанки, **не более 2 параллельных запросов** (3+ ловят WB rate limit 429 и DB statement timeout).
- Идемпотентный UPSERT по `rrd_id` — повторный прогон безопасен.
- Запуск из SQL: `SELECT net.http_post(url, headers, body, timeout_milliseconds := 120000)`.

## 3. Воронка продаж — общая основа для нескольких модулей

Таблица `wb_sales_funnel` (показы / клики / в корзину / заказы / выкупы / возвраты / оборачиваемость) — **переиспользуется**:

- **% выкупа** — для дашборда и колонок в аналитике
- **Оборачиваемость** — для решения об участии в акциях
- **Реклама** — расчёт CPC, CPM, конверсий по этапам, ROAS, ДРР (CR показы→клики, клики→корзина, корзина→заказ, заказ→выкуп)
- **Лайфсайклы товаров** — детект «застрял на этапе» (много показов, мало кликов = плохое фото; много кликов, мало заказов = плохая цена/описание)

**Источник:** WB API «Воронка продаж» (точный endpoint в процессе ресёрча, ежедневный cron).

## 4. Источники данных — только автоматика + одно ручное поле

**Принцип:** все метрики (% выкупа, оборачиваемость, маржа, комиссия, логистика, хранение, СПП, заказы, выкупы, возвраты, конверсии) — **автоматически из WB API**. Ничего ручного, кроме одного.

**Единственное ручное поле:** `sku_catalog.cost_price_rub` = «Себестоимость до ВБ» из UNIT.xlsx [лист Юнит, колонка 6].

Это значение **уже включает**:
- закупочную цену в Китае
- карго до РФ
- индивидуальную обработку / упаковку
- доставку до склада WB

Отдельных полей «фулфилмент» / «доставка до складов» **не заводить** — они часть «Себестоимости до ВБ».

Обновление `cost_price_rub` — только из UNIT.xlsx загрузкой (не ручным вводом в UI), источник фиксируется в `cost_price_source`.

## 4. Промо-акции WB — модель данных и решения

- **Несколько параллельных акций:** каждая пара (`promotion_id × nm_id`) — отдельная строка в `wb_promotion_items`. Финальная цена на витрине = `MIN(plan_price)` среди акций, где `user_participate = true`.
- **Решение пользователя:** колонки `user_participate BOOL`, `user_decided_at`, `user_note` в `wb_promotion_items`. NULL = ещё не решено.
- **Оборачиваемость = дни до распродажи стока.** Формула: `остатки на сегодня / средние продажи в день за последние 28 дней`. **Чем больше дней — тем хуже** (товар залёживается).
- **Границы оборачиваемости (для рекомендации участия в акции):**
  - **< 60 дней** — товар продаётся хорошо, акция не нужна (рекомендация по марже)
  - **60–90 дней** — акция полезна для ускорения распродажи
  - **> 90 дней** — срочно сливать, акция нужна даже при минусовой марже
- **Авто-акции (`type=auto`):** WB сам назначает скидку, выйти из API нельзя — только в ЛК. Эндпоинт `nomenclatures?inAction=true` возвращает текущий список SKU; `inAction=false` отдаёт 422.
- **Rate limit WB Promo API:** 10 req/мин, global limiter per seller. Между вызовами `nomenclatures` держать ≥2,5 с.

## 4. Секреты Supabase

- Один токен для всех WB-функций: **`WB_TOKEN_READ`** (на самом деле полный — с правами Статистика, Цены и скидки, Контент, Аналитика; имя историческое).
- Старое имя `WB_API_TOKEN` оставлено как fallback в коде (`Deno.env.get("WB_TOKEN_READ") ?? Deno.env.get("WB_API_TOKEN")`), но в env его держать не нужно.
- При отзыве WB токена (`401 "Access token withdrawn"`) — перевыпустить и обновить только `WB_TOKEN_READ`.
