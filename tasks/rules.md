## 1. Тестовая неделя для любых изменений в финансовых формулах

**Правило:** при добавлении новой колонки / коэффициента / формулы в `wb_reports_fact` или производные сущности (комиссия, СПП, выручка по карточке, маржа, etc.):

1. Делаем миграцию + правим маппинг в edge function.
2. **Сначала перезаливаем ТОЛЬКО тестовую неделю `2025-12-01 — 2025-12-07`** (отчёты `559705441` Основной + `559705442` По выкупам).
3. Сверяем с цифрами владелицы из её WB-кабинета и Excel `PL WB (нед)` (колонка `01.12-07.12`).
4. **Только после совпадения** раскатываем перезалив на весь год (12 месяцев × 1-2 параллельно).

**Почему:** у владелицы по этой неделе есть и WB-скриншоты, и Excel-сверка, и наша БД-сверка. Это «золотая» точка калибровки. Если новая формула на ней не сходится — глобальный перезалив = трата ресурсов + засорение БД мусором.

**Эталонные цифры за 01.12–07.12.2025** (сумма отчётов `559705441` + `559705442`):

| Метрика | Значение | Источник | Формула |
|---|---:|---|---|
| Продажи шт (Excel R7) | 246 | Excel | `SUM(quantity)` Продажи |
| **Продано по цене в карточке (Excel R14)** | **170 768 ₽** | Excel + WB скрин | `SUM(retail_price × quantity)` Продажи **− Возвраты руб (R22)** |
| Выручка ВБ реализовал (Excel R15 / WB «Продажа») | 114 665 ₽ | Excel + WB | `SUM(retail_amount)` net (Продажи − Возвраты) |
| Комиссия ВБ (Excel R17) | 53 235 ₽ | Excel | `R14 − R20` (т.е. карточка минус к перечислению — НЕ классическая комиссия, а полное удержание ВБ) |
| % комиссии (Excel R18) | 31,17% | Excel | `R17 / R14` |
| К перечислению (Excel R20 / WB «К перечислению за товар») | 117 533 ₽ | Excel + WB | `SUM(ppvz_for_pay)` |
| Возвраты руб (Excel R22) | 628 ₽ | Excel | Sum возвратов по retail_price |
| Возвраты шт (Excel R23) | 1 | Excel + WB | `COUNT(*)` doc_type_name='Возврат' |
| Логистика (WB скрин) | 18 495,37 ₽ | WB скрин | `SUM(delivery_rub)` |
| Хранение (WB скрин) | 6 021,16 ₽ | WB скрин | `SUM(storage_fee)` |
| Компенсация СПП (WB скрин, только Основной) | 24,33 ₽ | WB скрин | |
| Итого к оплате (WB скрин) | 93 015,89 ₽ | WB скрин | |

**Важно про СПП:**
- `ppvz_spp_prc` в WB API — **средневзвешенный** процент скидки СПП на конкретный товар, обычно ~20–25%.
- Реальная скидка от карточки за неделю получается выше (32,9% для этой недели), потому что в R14 владелица **вычитает возвраты**, а ещё работает накопительная скидка покупателя.
- **Правильная формула «по карточке» = `SUM(retail_price × quantity) для Продаж − SUM(retail_amount) для Возвратов`**, НЕ `retail_amount × (1 + spp_prc/100)`.

## 2. Перезалив исторических данных в WB API

- WB Statistics API отдаёт полную детализацию (storage_fee, acquiring_fee, spp_prc и т.д.) за весь 2025 год.
- Edge function упирается в wall-clock таймаут при периодах > ~3 месяцев.
- **Рабочая стратегия:** месячные чанки, **не более 2 параллельных запросов** (3+ ловят WB rate limit 429 и DB statement timeout).
- Идемпотентный UPSERT по `rrd_id` — повторный прогон безопасен.
- Запуск из SQL: `SELECT net.http_post(url, headers, body, timeout_milliseconds := 120000)`.

## 3. Воронка продаж — общая основа для нескольких модулей

Таблица `wb_sales_funnel` (показы / клики / в корзину / заказы / выкупы / возвраты / оборачиваемость) — **переиспользуется**:

- **% выкупа** — для дашборда и колонок в аналитике
- **Оборачиваемость** — для решения об участии в акциях
- **Реклама** — расчёт CPC, CPM, конверсий по этапам, ROAS, ДРР (CR показы→клики, клики→корзина, корзина→заказ, заказ→выкуп)
- **Лайфсайклы товаров** — детект «застрял на этапе» (много показов, мало кликов = плохое фото; много кликов, мало заказов = плохая цена/описание)

**Источник:** WB API «Воронка продаж» (точный endpoint в процессе ресёрча, ежедневный cron).

## 4. Источники данных — только автоматика + одно ручное поле

**Принцип:** все метрики (% выкупа, оборачиваемость, маржа, комиссия, логистика, хранение, СПП, заказы, выкупы, возвраты, конверсии) — **автоматически из WB API**. Ничего ручного, кроме одного.

**Единственное ручное поле:** `sku_catalog.cost_price_rub` = «Себестоимость до ВБ» из UNIT.xlsx [лист Юнит, колонка 6].

Это значение **уже включает**:
- закупочную цену в Китае
- карго до РФ
- индивидуальную обработку / упаковку
- доставку до склада WB

Отдельных полей «фулфилмент» / «доставка до складов» **не заводить** — они часть «Себестоимости до ВБ».

Обновление `cost_price_rub` — только из UNIT.xlsx загрузкой (не ручным вводом в UI), источник фиксируется в `cost_price_source`.

### Перспектива (ROADMAP): автоматический расчёт себеса

Сейчас `cost_price_rub` = вручную внесённая «Себестоимость до ВБ». В перспективе разложить её на компоненты, чтобы расчёт был автоматическим:

```
Себестоимость на ед. = Закуп Китай + Карго + Фулфилмент + Доставка до склада WB
```

Источники данных (у владелицы уже есть Excel-таблицы по этим темам):
- **Заказы в Китай** — закупочная цена + объём партии → формирует closure_price_per_unit
- **Поставки** — транспортные расходы (карго, транзит) → разносятся пропорционально на единицу
- **Фулфилмент (ФФ)** — расходы на ед. (приёмка, переупаковка, инд. обработка)
- **Доставка до склада WB** — платная, привязана к поставке

Когда модули заведутся:
- Новые таблицы: `china_orders` (уже есть), `china_order_items`, `supplies` (уже есть), `fulfillment_costs`, `delivery_to_wb`
- View `v_sku_cost_breakdown` — собирает себес из этих 4 источников по nm_id
- `sku_catalog.cost_price_rub` остаётся как «факт сейчас», но может пересчитываться скриптом из view

Это **обширный и важный** блок, отдельная задача. Сейчас просто фиксируем перспективу.

## 5. Промо-акции WB — модель данных и решения

- **Несколько параллельных акций:** каждая пара (`promotion_id × nm_id`) — отдельная строка в `wb_promotion_items`. Финальная цена на витрине = `MIN(plan_price)` среди акций, где `user_participate = true`.
- **Решение пользователя:** колонки `user_participate BOOL`, `user_decided_at`, `user_note` в `wb_promotion_items`. NULL = ещё не решено.
- **Оборачиваемость = дни до распродажи стока.** Формула: `остатки на сегодня / средние продажи в день за последние 28 дней`. **Чем больше дней — тем хуже** (товар залёживается).
- **Границы оборачиваемости (для рекомендации участия в акции):**
  - **< 60 дней** — товар продаётся хорошо, акция не нужна (рекомендация по марже)
  - **60–90 дней** — акция полезна для ускорения распродажи
  - **> 90 дней** — срочно сливать, акция нужна даже при минусовой марже
- **Авто-акции (`type=auto`):** WB сам назначает скидку, выйти из API нельзя — только в ЛК. Эндпоинт `nomenclatures?inAction=true` возвращает текущий список SKU; `inAction=false` отдаёт 422.
- **Rate limit WB Promo API:** 10 req/мин, global limiter per seller. Между вызовами `nomenclatures` держать ≥2,5 с.

## 6. Секреты Supabase

> **⚠️ ВАЖНО для AI: `WB_TOKEN_READ` — единый токен на ЧТЕНИЕ всех параметров (Статистика, Цены и скидки, Контент, Аналитика, Маркетплейс, Финансы, Продвижение). У владелицы выпущен ОДИН такой токен, его достаточно для любой нашей edge function.**
>
> **При 401 / `Access token withdrawn` от WB:**
> - НЕ просить владелицу зайти в кабинет / обновить Secret / выпустить новый токен.
> - НЕ предлагать «вручную проверить токен», «обновить GitHub Secret», «передеплоить функцию».
> - Считать что владелица обновляет токен сама когда узнаёт что он отозван — это её зона ответственности, не пользовательская задача от ИИ.
> - Зафиксировать ошибку в `ingestion_log`, сообщить факт («WB API возвращает 401 с N такого-то дня, код-часть исправна») один раз и не возвращаться к теме.
>
> **Любые попытки записывать через WB API (upload, change price, и т.п.) — НЕ работают**, токен это не позволит. В будущем для записи понадобится отдельный токен.

- Один токен для всех WB-функций: **`WB_TOKEN_READ`** (read-only, все категории).
- Старое имя `WB_API_TOKEN` оставлено как fallback в коде (`Deno.env.get("WB_TOKEN_READ") ?? Deno.env.get("WB_API_TOKEN")`), но в env его держать не нужно.

## 7. UI: одна страница — одна ширина

**Правило:** любая страница, таблица, график должны умещаться в ширину экрана без горизонтального скролла, если данные физически это позволяют.

**Что это значит на практике:**
- Если колонок таблицы много — пересмотри, какие реально нужны (бренд, доп. идентификаторы и т.п. убирай если они дублируют title/категорию)
- Длинные подписи сокращай и переноси на tooltip (`Видимость / Доверие / Ценность` → `В/Д/Ц` с расшифровкой при наведении)
- Прогресс-бары и multi-line ячейки сжимай до 1 строки если возможно
- Графики: используй адаптивные viewBox/PAD, не фиксированный пиксельный max-width
- Перед добавлением новой колонки/блока — спросить себя «помещается на 1366×768 без скролла?»

**Когда горизонтальный скролл всё-таки оправдан:**
- Сравнительные таблицы где ВСЕ колонки обязательны (P&L по статьям × 10+ статей)
- Wide-screen аналитика которая не имеет смысла на узком экране

В этих случаях оборачивать в `overflow-x-auto` внутри карточки (не наружу страницы), чтобы скроллилась только таблица, а не весь viewport.

## 8. Период по умолчанию — 30 дней

**Правило:** все агрегации, метрики, KPI и аналитика по умолчанию считаются за **последние 30 дней**, если в UI нет явного селектора периода.

**Где применяется:**
- Воронка продаж (open / cart / order / buyout)
- Конверсии, % выкупа, рейтинги
- Топ-5 товаров, категории
- Любые карточки с дельтой «за месяц»

**Исключение:** расчёт поставок и прогноз запасов — там окно исходных данных оговаривается отдельно для каждой задачи (типично 60-90 дней для стабильности прогноза).

**Почему 30:**
- Совпадает с тем что показывает WB-кабинет (точка опоры для владелицы).
- На длинных окнах метрики «размываются» — пользователь не видит свежих изменений.
- Для дельт «за месяц» нужен предыдущий месяц как база.

**Если окно агрегации в БД больше (например `wb_sales_funnel_period` = 60 дней):**
- Краткосрочно: в UI показывать с пометкой «за окно фетча», объяснить что период фетча > 30.
- Долгосрочно: задача в backlog — поменять параметр в edge function на 30 дней + перезалить.

## 9. Живой TODO + автономная работа

**Правило:**

1. **Каждый фикс/баг/правка от пользователя → сразу в TODO-список** (`tasks/ITERATION_PLAN.md` или эквивалент в проекте). Не держать в голове, не пропускать. Формат — чекбокс `- [ ]` с коротким описанием.

2. **Если пользователь молчит → беру следующий пункт из TODO и делаю сам.** Без вопросов «продолжить?» если задача чёткая и в моей компетенции (код, миграции, query, UI). Молчание ≠ остановка.

3. **При возвращении пользователя — сначала отчёт.** Перед новой задачей: «пока тебя не было, сделал A, B, C; в работе D; жду E». Только потом — следующий шаг.

**Что НЕ делаю автономно:**
- Деструктивные действия (drop tables, force push, mass update БД).
- Архитектурные решения без согласования (новая схема, новый сервис).
- Внешние коммуникации (комментарии в чужих PR, посты).

**Где исключения:** если в задаче из TODO явно стоит флаг «спросить пользователя» — спрашиваю.

## 10. Полная цепочка push → main (zero-touch для пользователя)

**Принцип:** пользователь не должен ловить технические баги (build failed, lint, types, unused, missing PR, отстающий main). Я довожу каждый push до **READY в main** сам.

### Цикл после любого commit

```
edit → mental-check → commit → push → присылаю PR ссылку → жду CI → проверяю build → fix если ERROR → ждать merge → проверяю main
```

### Шаги

**1. Перед `git commit` — mental check:**
- Удалил ли неиспользуемые импорты? (`ChannelsDonut`, `Badge`, `CardTitle`, ...)
- Удалил ли неиспользуемые переменные? (`channels`, `deltaYesterday`, `fmt`, ...)
- Нет ли висящего `<<<<<<< HEAD` после merge?
- Все ли helper-функции реально вызываются? (если объявил `fillHours`, `DeltaPill` — использую их или удаляю).

**2. После `git push`:**
- **Проверить открыт ли PR с этой ветки в main.** Если нет → `mcp__github__create_pull_request(base='main', head='<ветка>', draft=false)`.
- **Сразу прислать ссылку PR пользователю в чат** (`https://github.com/owner/repo/pull/NNN`).

**3. Через 30-60 секунд после push (CI стартует):**
- `mcp__Vercel__list_deployments` — найти свежий deployment с моим SHA.
- Если `state=BUILDING` → ждать ещё 1-2 минуты.
- Если `state=ERROR` → `get_deployment_build_logs` → найти причину → fix → goto шаг 1.
- Если `state=READY` → ✅ можно идти к следующей задаче.

**4. После того как пользователь смержит PR:**
- `pull_request_read` → проверить `merged=true`.
- `git fetch origin main && git log origin/main -1` → проверить что новый коммит в main.
- Если на ветке появятся новые коммиты позже — **сразу открыть следующий PR** (GitHub не делает это автоматически после squash-мержа).

### Что пользователь НЕ должен ловить
- Build failed (ESLint, типы, missing import)
- «main не обновляется» (значит я не открыл PR)
- «PR отсутствует» (создаю сразу после push)
- Merge conflicts (резолвлю сам, не показываю)
- Vercel ERROR деплои в истории (фикшу до того как пользователь увидит)

### Что пользователь МОЖЕТ ловить
- Функциональные баги: логика, UI, цифры, формулы, расположение блоков, тексты.
- Архитектурные вопросы: «правильно ли так делать?».
- Новые задачи и фиксы.

## 11. Делегирование агентам — основной режим работы

**Правило:** моя роль — архитектор и приёмщик, а не исполнитель.

**Что делаю Я:**
1. **Принимаю решение** что и как делать (формула P&L, схема таблицы, структура компонента, расположение блоков).
2. **Пишу чёткий план** для агента: какие файлы тронуть, что именно изменить, как проверить.
3. **Принимаю работу:** читаю diff, проверяю что сделано, мержу или возвращаю на исправление.

**Что делает АГЕНТ:**
- Реализация: написать компонент, query, миграцию, тесты.
- Поиск по репо, чтение больших файлов.
- Параллельные независимые задачи (например, два разных компонента одновременно).

**Когда сам пишу:**
- Тривиальные правки 1-3 строк (быстрее самому).
- Когда задача требует контекста сессии, который сложно передать.
- Архитектурные миграции (когда формула P&L — не очевидно).

**Доступные агенты:**
- `general-purpose` — для написания кода, исследования, многошаговых задач
- `Explore` — read-only поиск кода
- `claude-code-guide` — про Claude Code/SDK/API

**Правило параллелизма:** если независимых задач 2+ — запускаю агентов одной сессией (multiple Agent tool calls in one message) → ждать результат → собрать в один коммит.

## 11a. Выбор модели для агента

**Дефолт: `sonnet`** (general-purpose) — 90% задач: компонент, query, миграция, тесты, рефакторинг.

**`haiku`** — тривиал: поиск файлов, чтение, простые правки 1-3 строки. Дёшево + быстро.

**`opus`** — только: архитектура новой системы, сложный дебаг, BIG-задачи требующие глубокого reasoning. Дорого, в работе использовать редко.

**Правило:** не запускать `opus` без явной необходимости. Sonnet справится с подавляющим большинством — её и используем по умолчанию.

## 13. Расширение автономии (2026-06-15)

**Можно самостоятельно (без спроса):**

1. **Самостоятельный поиск багов** — регулярно запускать UAT-агентов на страницы/компоненты, фиксировать находки в `todo.md`.
2. **Фиксить баги, найденные при UAT** — без отдельного согласования. Сразу делегировать починку агенту.
3. **Принимать решения о компактных рефакторингах** — пагинация/виртуализация/дебаунс/индексы/обновление зависимостей с понятным upside. До 1 файла — сам. Большие touch'и (>5 файлов / архитектура) — спрашивать.
4. **Запускать `migrate.yml`** через `workflow_dispatch` когда нужно применить миграции — без подтверждения.
5. **Мержить PR самостоятельно** через `mcp__github__merge_pull_request` (squash) — но **в правильном порядке**, чтобы PR от агентов не обгоняли друг друга:
   - Сначала мерж PR где меньше всего конфликтов (старые → новые).
   - Если PR-Б был открыт после PR-А и зависит от него — сначала PR-А, потом ребейзить PR-Б.
   - После каждого мержа — `git fetch origin main` локально, чтобы не отстать.

**По-прежнему спрашиваю:**
- Архитектурные решения (новая схема БД, новый сервис, смена формулы P&L)
- Деструктивные действия (drop tables, force push, mass UPDATE)
- Внешние коммуникации (комментарии в чужих PR, посты, email)
- Большие фичи с >1 разумным путём
- Когда нашёл много багов (>5) и нужен приоритет

## 14. Один пункт → до зелёного мержа → следующий

**Правило:** беру **только один** пункт из todo за раз. Цикл:

```
1. Взять пункт → сделать (сам или через агента)
2. Commit → push → авто-открытый PR
3. Дождаться CI зелёного (если ERROR — fix)
4. MERGE в main через mcp__github__merge_pull_request (squash)
5. Обновить tasks/todo.md (закрыть пункт)
6. Только теперь брать следующий пункт
```

Не накапливать висящие PR. Не браться за второе дело до того как закрыто первое.

### Параллельные агенты — когда можно, когда нельзя

**МОЖНО** параллелить если:
- Задачи затрагивают **РАЗНЫЕ файлы** (агент A пишет компонент X в `features/foo/`, агент B пишет миграцию в `supabase/migrations/`)
- В брифе агенту явно указано «трогать только эти файлы»

**НЕЛЬЗЯ** параллелить если:
- Одни и те же файлы (page.tsx, общий типы, общая query)
- Один пункт зависит от другого (агент B использует функцию которую делает агент A)

**Если очень нужны 2 пересекающиеся задачи** — выполнять **последовательно**: запустить агента A → дождаться → commit + push → потом агента B.

### Дисциплина при чехарде

Если уже накопились 5+ PR от агентов и они конфликтуют:
1. Закрыть все кроме самого первого, ничего не мерж'я
2. Тот первый довести до мержа
3. Сделать `git fetch origin main` + `git merge origin/main` на ветке
4. Один за другим перезапустить остальных, **меняя scope** чтобы не пересекались.

## §16 Замена `.range(0, X)` на RPC агрегацию — обязательная сверка

**Правило:** при переписывании любого запроса `supabase.from(...).range(0, N)` где N ≥ 50_000 (то есть «тянем сырьё в Node для агрегации в JS») на серверную RPC:

1. **До коммита** — через `mcp__Supabase__execute_sql` вызвать ОБЕ версии параллельно:
   - старая JS-логика воспроизводится в SQL (`SELECT ... + WHERE filters + sum/count в SQL аналогом JS reduce`)
   - новая RPC через `SELECT ... FROM public.get_xxx(...)`
2. Сравнить ключевые цифры (count, sum, distinct count и т.п.). **Идентичность — условие коммита.**
3. **Если расходятся — НЕ коммитить.** Записать диагноз: старое значение, новое значение, гипотеза причины (округление, NULL-обработка, фильтр). Эскалировать владелице.
4. В commit body — **обязательно** строка «Сверка через MCP execute_sql: X ✓» с конкретными числами обеих версий.

**Почему:** у `wb_reports_fact` нет автотестов формул. JS reduce и SQL агрегаты могут разойтись на:
- NULL-обработке (`COALESCE(x, 0)` vs `toNumber(x)`)
- Порядке округления (`Math.round` per-row vs after-sum)
- Типах (numeric vs float vs string-from-postgres)
- Семантике `quantity > 0` (возвраты vs продажи)

**Образец паттерна:** PR #147 (data-quality) — RPC `get_channel_gap_dates`, сверка `wb_sales 13/wb_reports 25 distinct days`. Полная цепочка: миграция через `mcp__Supabase__apply_migration` → сверка через `execute_sql` → правка TS → `tsc/eslint/build` → коммит → push → авто-PR.

**Правило миграции (схема):** каждая RPC — `SECURITY INVOKER`, `SET search_path = ''`, `STABLE`, `LANGUAGE sql`, явный `GRANT EXECUTE ... TO authenticated, service_role`, `COMMENT ON FUNCTION ... IS '...замена .range(...) в <file>'`.

_Источник: SellerBase 2026-06-21 — рефакторинг 9 файлов из аудита 2026-06-20 без регрессий благодаря этому циклу._

## §18 Каждая номенклатура — отдельный товар (2026-08-27)

**Правило:** любой `nm_id` в ассортименте — самостоятельная товарная единица.
Цвета, размеры и варианты одной модели не считаются «одним товаром в разных обличьях».

**Что из этого следует — и это не формальность, а прямые последствия в работе:**

| | следствие |
|---|---|
| **Ядро** | у каждой номенклатуры своё, целиком. Нельзя рассчитывать, что соседний цвет «дотянет» запросы |
| **Наименование** | своё и **непохожее на соседей**. Дословно одинаковые наименования у двух своих карточек — это каннибализация, а не экономия |
| **Описание** | своё. Копия текста между своими карточками — дублирующий контент, а не переиспользование |
| **Характеристики** | заполняются по каждой карточке отдельно |
| **Отзывы и рейтинг** | принадлежат номенклатуре и **не объединяются** при склейке. «Собрать отзывы в одну карточку» невозможно в принципе |
| **Ревизия и отчёты** | единица наблюдения — `nm_id`, а не модель и не группа |

**Про склейку.** Цветная склейка в кабинете — это только переключатель для покупателя.
Она не сливает карточки: у каждого цвета остаются свой поиск, своё наименование,
своё описание и свои отзывы. Наличие или отсутствие склейки **не меняет** ничего из таблицы выше.

**Отдельно — про слово «склейка», его легко перепутать:**

- **склейка карточек** — объединение цветов в кабинете (предмет этого правила);
- **склейка значений** — несколько понятий, слепленных через запятую в одном значении
  характеристики. Это дефект заполнения и с 01.05.2026 основание для теневого бана
  (см. `docs/seo/wb-ranking-2026.md`).

Эти два значения в обсуждениях не смешивать — называть полностью.

**Почему:** на разборе роликовых массажёров `ACRB1MS101BL/PN/RJ` две карточки имели
дословно одинаковое наименование, а у двух других описание совпадало побайтово.
Это следствие взгляда «это же один товар в трёх цветах». Товаров три.

_Источник: SellerBase 2026-08-27 — разбор группы роликовых массажёров._

## §19 Пересборка карточек: факты → план → одобрение → действие (2026-08-27)

**Правило:** карточки любой группы собираются по регламенту
[`docs/seo/card-assembly.md`](../docs/seo/card-assembly.md), в четыре фазы и без их перестановки.

| фаза | кто | чем заканчивается |
|---|---|---|
| свод фактов | ИИ сам | что есть и чего нет — **с частотностями** |
| план | ИИ предлагает | план по полям, наименованиям, текстам с обоснованием |
| **одобрение** | **владелица** | решения по ключам, тону, отсечениям, дефектам |
| действие | ИИ | готовые значения и тексты в репозитории |

**Три вещи, которые нарушать нельзя:**

1. **Фотографии товара — до разбора.** Конструкция не достраивается по отзывам, габаритам
   и инфографике карточки: инфографика может быть отрисована или взята со стока.
2. **Пять источников семантики, а не один.** Выгрузка частотностей, теговые страницы WB,
   **наименования ТОП-50 выдачи** по главному запросу, внешние тематические источники,
   наши отзывы. Выгрузка замкнута на то, что в карточках уже написано, и пропущенного
   не покажет. ТОП-50 собирает владелица (из контейнера выдача не достаётся), разбирает
   скрипт `scripts/analyze_top50.py`: он показывает постоянное ядро схемы и чего в наших
   наименованиях против него не хватает.
3. **Частотность у каждого ключа.** Без цифры ключ не попадает ни в свод, ни в план.
   Цена отсечения считается, а не подразумевается.

**Фаза одобрения не совмещается с действием.** Ключи, тон, содержание текстов, что считать
дефектом, какие поля не заполняем, очерёдность групп — решает владелица.

**Почему:** за один день 27.08 правило доказалось трижды. Наименования мячей, собранные
сразу по выгрузке, вышли из четырёх теговых страниц WB, потому что из них выбросили
«с шипами» и «жесткий». Назначение по диаметру из выгрузки не выводилось вообще — ответ
дали конкуренты и внешние источники, и там же нашлись значения справочника «Зона массажа»,
которых не стояло ни в одной из наших карточек. А фотография роликового массажёра сняла
«блокер», выдуманный из габаритов.

_Источник: SellerBase 2026-08-27 — три разобранные группы._

## §20 Ключи распределяются по заказам, а не по частотности (2026-08-28)

**Правило:** наименование карточки собирается по годовому отчёту кабинета —
по тому запросу, на котором карточка **реально продаёт**, а не по самому
частотному в группе. Частотность говорит, сколько людей ищет; заказы говорят,
кто из них покупает у нас.

**Обязательная проверка перед закрытием группы** — тест «топ-запрос против
наименования»: по каждой карточке взять запрос с наибольшим числом заказов
за год и убедиться, что его слова стоят в заголовке. Процедура и остальные
шесть проверок — [`docs/seo/card-assembly.md`](../docs/seo/card-assembly.md)
§П1–§П7.

**Разбор группы — по двум срезам** (там же §1.2.2): Эвирма отвечает, как
выглядит полка, годовой отчёт — где мы продаём. Позиции между срезами
не сравниваются. Нет одного среза — запросить у владелицы, на одном не разбирать.

**Почему.** За 28.08 тест поймал ошибку в каждой из четырёх групп подряд:

- таблетницы — фраза «на неделю 2 приема» держит 510 заказов из 684 и ранжирует
  все девять живых карточек, а редакция 27.08 убирала её из пяти заголовков
  ради непохожести: 143 заказа за год;
- мешки — `2BW202WH` называлась «Чехол», при том что все её 22 заказа идут
  с «мешок для стирки колготок капроновых», а на «чехол» — ноль;
- мячи — `107BL` потерял «жесткий» третий раз подряд;
- массажёры — `101BL` вела на «массажер для тела» по частотности 158 637,
  за год ни одного заказа со словом «тело»; Эвирма показала почему —
  87% полки реклама, весь топ-10 электрический.

**Запрет, отдельно.** Публичную выдачу WB не парсить ни при каких условиях
(решение владелицы 28.08, риск бана): чужая полка берётся только из платного
сервиса аналитики, свои данные — только из официального API продавца.

_Источник: SellerBase 2026-08-28 — четыре группы, годовой отчёт 344 строки._

## §21 В карточках только короткий дефис (2026-09-03)

**Владелица, 03.09:** «Длинные тире это признак ИИ. В моих описаниях только
короткий дефис».

Ни «—», ни «–» не попадают в наименование, описание, комплектацию и любое
другое значение, которое уходит в кабинет. Только «-».

Правило применяется **на выходе**, при записи ячейки книги
(`no_long_dash` в `scripts/build_cards_xlsx.py`), а не в разборах: там тире
служебное — им отделяется пояснение от значения («нужен замер — в поле 6 см,
на слайде 50 мм»), и `strip_note` по нему режет. Заменить его в разборе —
сломать разбор.

Проверка перед отдачей файла: в листах групп ноль ячеек с «—» и «–».
Служебные листы («Как читать файл», «Инфографика», «Размеры и вес») правило
не затрагивает — они в кабинет не заливаются.

### §21.1 Комплектация — каждая позиция с заглавной буквы (2026-09-03)

**Владелица, 03.09:** «С большой буквы комплектацию впредь».

Позиции разделены «;», и заглавной становится первая буква **каждой**,
а не только первой позиции: «Круглый контейнер для таблеток на день - 7 шт.;
Футляр-органайзер - 1 шт.». Остальные буквы не трогаем — внутри встречаются
размеры и обозначения, которым регистр менять нельзя («15 × 17 см», «TPR»).

Применяется там же, на выходе (`capitalized_items`). Оба правила §21
переносятся в книгу владелицы молча: это оформление, а не смысловая правка,
согласовывать нечего.

## §22 Подсветка в книге сверяется с живым кабинетом (2026-09-03)

**Владелица, 03.09:** «в файле сейчас есть индикация, но я уже на сайте
поменяла. Надо сверить с кабинетом и убрать сделанные индикации, оставить
только то, что надо доделать».

Зелёная ячейка означает ровно одно: **этого ещё нет в кабинете**. Не «разбор
предлагает», не «я так решил» — а «правка не залита». Как только владелица
заливает её на сайте, ячейка обязана погаснуть сама.

### Как это устроено

| Источник | Что даёт | Приоритет |
|---|---|---|
| `docs/seo/cabinet-live.json` | что реально стоит в карточках сейчас | **высший** |
| `docs/seo/cabinet-export.json` | ручная выгрузка кабинета | ниже |
| разборы `docs/seo/descriptions/*.md` | что предлагаем поставить | сравнивается с первыми двумя |

`cabinet-live.json` собирается из `sku_catalog` после `fetch-wb-content` —
официального API продавца. Ручная выгрузка устаревает в момент первой же
заливки, поэтому одна она негодна.

### Порядок сверки перед отдачей файла

1. Запустить синк кабинета:

```sql
SELECT net.http_post(
  url := 'https://hcebwgjgppwaguqittpi.supabase.co/functions/v1/fetch-wb-content',
  headers := jsonb_build_object(
    'Content-Type','application/json',
    'Authorization','Bearer '||(SELECT decrypted_secret FROM vault.decrypted_secrets WHERE name='service_role_key'),
    'X-Cron-Secret',(SELECT decrypted_secret FROM vault.decrypted_secrets WHERE name='cron_shared_secret')),
  body := '{}'::jsonb, timeout_milliseconds := 180000);
```

2. Проверить результат в `public.ingestion_log` (не в `cron.job_run_details`).
3. Пересобрать `cabinet-live.json` по группе, которую проверяем.
4. Пересобрать книгу и перенести в файл владелицы через
   `scripts/apply_to_book.py` — он несёт заливку вместе со значениями,
   включая её снятие.
5. Отчитаться цифрой: было подсвечено столько-то, стало столько-то.

### Чего делать нельзя

- **Не подсвечивать залитое.** Это обесценивает индикацию: владелица перестаёт
  доверять цвету и проверяет всё подряд руками.
- **Не гасить неподтверждённое.** Если карточки нет в кабинете (как `101WH`
  у таблетниц), подсветка остаётся — иначе правка потеряется.
- **Не трогать колонку артикула.** Там пометки владелицы: зелёный — карточка
  обработана, красный — выведена из продажи. Это её разметка, не наша.

### Описания — сверка по длине

Полный текст в слепок не кладём, он на полторы тысячи знаков. Судим по длине
с допуском 15 %: наши описания укладываются в 1000–1500 знаков, прежние
занимают 2700–3100. Сравнивать по началу текста нельзя — владелица
переписывает первую строку под изменённое наименование.

Ограничение честное: если она перезальёт описание другой длины, сверка его
не увидит. Тогда — обновить слепок и пересобрать.

## §23 Три источника разбора: Джем, Эвирма, Промопульт (2026-09-03)

**Владелица, 03.09:** «У нас два среза — промопульт, эвирма — и джем».

Группа считается разобранной, только когда сведены все три. Ни один
не заменяет другой: они отвечают на разные вопросы.

| Источник | Что это | На какой вопрос отвечает |
|---|---|---|
| **Джем** | годовой отчёт поисковых запросов из кабинета, фильтр «Заказывали» | по каким словам у нас **покупают**, на каких позициях и с какой конверсией |
| **Эвирма** | срез выдачи по запросу, 100 позиций | **кто рядом**: цены, доля рекламы, отзывы, какой товар реально продаётся в этом запросе |
| **Промопульт** | выгрузка «Кластеры: сравнение позиций» | что **привязано** к карточке и какие кластеры существуют, включая те, где у нас нет заказов |

### Чего не видит каждый

- **Джем** выгружается с фильтром «Заказывали» — спрос без продаж в него
  не попадает вообще. Кластер, по которому мы ни разу не продали, там не виден.
- **Эвирма** не знает наших заказов: она показывает рынок, а не нас.
- **Промопульт** не содержит позиций и цен конкурентов (подтверждено
  владелицей). Частотности его кластеров нельзя сравнивать с частотностями
  Джема — источники разные (§П4).

### Что даёт только пересечение

Разборы 03.09 показали: главные находки лежат ровно на стыке.

- **Шпатели.** Джем: все заказы с «скребок для теста». Эвирма: в топ-20
  «шпателя кондитерского» продаются палетки для крема. Промопульт: «скребка»
  в ядре нет вовсе. Один источник дал бы четверть картины.
- **Пробки.** Джем: три карточки разошлись по трём разным словам.
  Промопульт: при этом все тянут одно ядро. Эвирма: ниша доступная,
  органики 11 из 18.
- **Ножи.** Джем: обе карточки на одном запросе, позиции 58 и 66.
  Эвирма: в топе вообще нет нашей конструкции — там ролики, у нас полумесяц.

### Порядок

1. Фотографии карточки от владелицы — **до** всего остального (§П0: конструкцию
   по отзывам и габаритам не достраиваем).
2. Джем по артикулам группы.
3. Эвирма по главному запросу группы.
4. Промопульт: что привязано и что в ядре лишнее.
5. Сверка кабинета (§22) и только потом правки.

## §24 Расхождение ключа и товара обсуждаем, а не отбрасываем (2026-09-03)

**Владелица, 03.09:** «Это всегда обсуждаем. Мы можем хотеть вывести запрос
в топ — подключим рекламу. Потому топовые запросы не откидываем, а включаем
в названия, описания, характеристики, даже если они пока не тянут ключи.
Просто эти моменты фиксировать надо и подстраивать текстовую воронку
и фото-воронку под топ-ключи».

### Правило

Частотность запроса — не повод его снять. Решение «ведём или нет» принимает
владелица, ИИ его не принимает молча.

Когда ключ крупный, а карточка по нему сейчас слаба или товар отличается
от того, что ждёт покупатель, — это не приговор ключу. Это задача:
довести карточку до запроса, а не запрос убрать из карточки.

| Что делаем | Как |
|---|---|
| **Фиксируем расхождение** | пишем в разборе: чего ждёт запрос, что даёт товар, где разрыв |
| **Ключ оставляем** | в наименовании, описании и характеристиках, даже если позиции пока низкие |
| **Подстраиваем текстовую воронку** | описание отвечает на ожидание запроса: чем наш товар решает ту же задачу |
| **Подстраиваем фото-воронку** | слайды показывают то, ради чего пришли по этому ключу |
| **Готовим к рекламе** | вывод в топ — рабочий сценарий, карточка должна быть к нему готова |

### Единственное исключение — товар физически не выполняет задачу

Ключ снимается, только когда покупатель по нему получает вещь, которая
**ломается или не работает** в заявленном сценарии, и это возвращается
жалобами и возвратами.

Прецедент: **шампанское у пробок.** Владелица 03.09: «эти пробки для
шампанского не годятся, их выбивают, люди жалуются, что она вылетает».
Давление газа выталкивает пробку из горлышка — никакой текст и никакая
фотография этого не исправят. Сняты «пробка для шампанского многоразовая»
21 693, «крышка для шампанского» 4 163 и «закрывашка для шампанского» 2 875,
пятая часть частотности группы.

Отличие от обычного расхождения: там товар делает работу, просто выглядит
иначе, чем ждали, — и это лечится воронкой. Здесь товар работу не делает.

### Что при этом всё равно нельзя

Заявлять свойство, которого у товара нет. Это не про выбор ключей,
а про честность карточки:

| Группа | Формулировка | Почему убрана |
|---|---|---|
| Игрушки | «на верёвке» | подвес резиновый, в отзывах «мяч на РЕЗИНКЕ!» с единицей |
| Игрушки | «суперпрочный» | мяч полый, отзывы бьют ровно в это слово |
| Ножи | «антибактериальное покрытие» | ни один слайд не подтверждает |

Разница с ключами: ключ говорит, **что человек искал**, а характеристика —
**что он получит**. Первое можно и нужно захватывать шире, второе обязано
совпадать с товаром.

### Как это выглядит в разборах

Расхождения, найденные 03.09, остаются в файлах как задачи на воронку,
а не как повод убрать ключ:

- **Шпатели.** «Шпатель кондитерский» 29 285 — в топе палетки для крема,
  у нас скребок для теста. Ключ оставлен, наименование ведёт оба слова;
  слайды нужно дополнить сценарием работы с кремом или признать, что
  карточка идёт в запрос «скребок».
- **Ножи для пиццы.** В топ-16 только круглые ролики, у нас качающийся
  полумесяц. Ключ «нож для пиццы» 204 358 оставлен, в наименование добавлено
  слово «качающийся», описание объясняет разницу — начинка не съезжает.
  Фото-воронка это уже показывает.
- **Мешки.** «Мешок для стирки обуви» 511 394 — самый частотный запрос
  категории, у карточек ноль привязанных кластеров. Ключ не снимаем,
  а привязываем.

## §25 Блок «Честно» упразднён — говорим преимуществами (2026-09-03)

**Владелица, 03.09:** «Раздел "Честно" упразднить во всех карточках. Не надо
давать даже намёка. Просто не говорим о недостатках. Переводим всё
в преимущества. "Честно" упраздняем для всей номенклатуры».

Блока «Честно» в описаниях больше нет ни у одной группы. Ограничения,
предупреждения и «этот товар вам не подойдёт, если…» из текстов убраны.

### Как переводить, а не вычёркивать

Убрать абзац — половина работы. Полезный факт из него остаётся, но подаётся
со стороны выгоды.

| Было | Стало |
|---|---|
| «Мяч полый, собака с серьёзной челюстью прогрызает его за игру» | «Мяч полый внутри - он легче монолитного, летит дальше и выше отскакивает» |
| «Слабое место скакалки - где трос входит в ручку, оболочка стачивается» | «49 стальных нитей закрыты резиновой оболочкой: она принимает трение на себя, трос внутри остаётся целым» |
| «Тканевая резинка растягивается, сопротивление падает на 10-15 % за полгода» | «Плетение с латексной нитью возвращает форму после растяжения; стирайте вручную - упругость держится дольше» |
| «Каркас не складывается плоско, занимает место как коробка» | «Каркас держит форму постоянно: чашки не сминаются ни под весом белья, ни на отжиме» |
| «Хлопковый канат распускается, собака может глотать нити» | «Хлопковые волокна работают как зубная нить: снимают налёт и массируют дёсны» |
| «Для мягкого поверхностного массажа не подходит» | фраза убрана, остаётся «воздействие точечное и глубокое» |

Правило перевода: **факт сохраняем, оценку меняем на выгоду**. Полый мяч
остаётся полым — но это лёгкость, а не слабость. Жёсткий ролик остаётся
жёстким — но это глубокая проработка, а не дискомфорт.

### Тонкости не выпячиваем, но и не убираем

**Владелица, 03.09:** «Не выпячивать такие тонкости, как полый. Но не убирать.
А аккуратно вставить. И так во всех карточках».

Факт остаётся в тексте, но не выносится в начало абзаца и не подаётся как
оговорка. Он встраивается в предложение о выгоде.

| Выпячено | Аккуратно |
|---|---|
| «Мяч полый внутри - он легче монолитного» | «Мяч заметно легче монолитного того же диаметра… Упругая стенка держит форму» |
| «Ролики твёрдые, давление ощутимое» | «Нажим доходит до мышцы под слоем ткани» |

Слово, которым покупатель может испугаться, заменяется на то, что он получит:
не «полый», а «лёгкий» и «упругая стенка»; не «твёрдый и давит», а «нажим
доходит до мышцы».

### Что это не отменяет

Заявлять свойство, которого у товара нет, по-прежнему нельзя (§24).
Перевод в преимущества — про **интонацию**, а не про выдумывание.
«Суперпрочный» в наименовании работает как ключ; в характеристиках
и описании свойств полого мяча мы его не утверждаем.

### Риск, о котором сказано владелице один раз

Блок «Честно» страховал от возвратов: покупатель с бойцовой собакой узнавал
про полый мяч до покупки, а не после. Без него часть таких покупок вернётся
отзывом. Решение принято владелицей осознанно, к обсуждению не возвращаемся.

## §26 Одна точка входа на контур (2026-09-03)

**Владелица, 03.09:** «У нас правило одна точка входа».

У каждого рабочего контура ровно **один** файл, с которого начинается работа.
Он содержит карту раздела: что где лежит, в каком порядке читать, чем
пользоваться. Всё остальное — листья, на которые точка входа ссылается.

| Контур | Точка входа |
|---|---|
| Карточки, тексты, SEO | `docs/seo/README.md` |
| Готовые описания по группам | `docs/seo/descriptions/README.md` |
| Правила проекта | `tasks/rules.md` (этот файл) |
| Текущие задачи | `tasks/todo.md` |
| Журнал сессий | `tasks/SESSION_LOG.md` |
| Классификация и маркировка | `docs/marking/codes-marking.md` |
| Сессия Claude | `CLAUDE.md` |

### Что из этого следует

**Новый файл в разделе — строкой в его точке входа, в том же коммите.**
Файл, которого нет в карте, для следующей сессии не существует: его
не найдут и напишут второй такой же.

**Второго входа не заводим.** Если для темы нужен отдельный документ — он
лист, а не вход. Признак нарушения: два файла начинаются словами «с этого
файла начинается работа с…».

**Дубль темы схлопывается в тот файл, который уже указан в карте.** Так
03.09 `fill-plan/README.md` был удалён, а метод перебора полей перенесён
в `card-assembly.md` — регламент уже был точкой входа для сборки карточки.

**Карта отражает и то, что отложено.** Раздел, работа по которому
приостановлена, остаётся в карте с пометкой — иначе он теряется.

### Проверка перед коммитом

Добавил файл в `docs/seo/`, `docs/marking/`, `tasks/`, `scripts/` — открой
точку входа контура и убедись, что файл там назван. Не назван — либо
дописать строку, либо файл не нужен.
