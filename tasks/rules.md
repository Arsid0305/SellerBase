## 1. Тестовая неделя для любых изменений в финансовых формулах

**Правило:** при добавлении новой колонки / коэффициента / формулы в `wb_reports_fact` или производные сущности (комиссия, СПП, выручка по карточке, маржа, etc.):

1. Делаем миграцию + правим маппинг в edge function.
2. **Сначала перезаливаем ТОЛЬКО тестовую неделю `2025-12-01 — 2025-12-07`** (отчёты `559705441` Основной + `559705442` По выкупам).
3. Сверяем с цифрами владелицы из её WB-кабинета и Excel `PL WB (нед)` (колонка `01.12-07.12`).
4. **Только после совпадения** раскатываем перезалив на весь год (12 месяцев × 1-2 параллельно).

**Почему:** у владелицы по этой неделе есть и WB-скриншоты, и Excel-сверка, и наша БД-сверка. Это «золотая» точка калибровки. Если новая формула на ней не сходится — глобальный перезалив = трата ресурсов + засорение БД мусором.

**Эталонные цифры за 01.12–07.12.2025** (сумма отчётов `559705441` + `559705442`):

| Метрика | Значение | Источник | Формула |
|---|---:|---|---|
| Продажи шт (Excel R7) | 246 | Excel | `SUM(quantity)` Продажи |
| **Продано по цене в карточке (Excel R14)** | **170 768 ₽** | Excel + WB скрин | `SUM(retail_price × quantity)` Продажи **− Возвраты руб (R22)** |
| Выручка ВБ реализовал (Excel R15 / WB «Продажа») | 114 665 ₽ | Excel + WB | `SUM(retail_amount)` net (Продажи − Возвраты) |
| Комиссия ВБ (Excel R17) | 53 235 ₽ | Excel | `R14 − R20` (т.е. карточка минус к перечислению — НЕ классическая комиссия, а полное удержание ВБ) |
| % комиссии (Excel R18) | 31,17% | Excel | `R17 / R14` |
| К перечислению (Excel R20 / WB «К перечислению за товар») | 117 533 ₽ | Excel + WB | `SUM(ppvz_for_pay)` |
| Возвраты руб (Excel R22) | 628 ₽ | Excel | Sum возвратов по retail_price |
| Возвраты шт (Excel R23) | 1 | Excel + WB | `COUNT(*)` doc_type_name='Возврат' |
| Логистика (WB скрин) | 18 495,37 ₽ | WB скрин | `SUM(delivery_rub)` |
| Хранение (WB скрин) | 6 021,16 ₽ | WB скрин | `SUM(storage_fee)` |
| Компенсация СПП (WB скрин, только Основной) | 24,33 ₽ | WB скрин | |
| Итого к оплате (WB скрин) | 93 015,89 ₽ | WB скрин | |

**Важно про СПП:**
- `ppvz_spp_prc` в WB API — **средневзвешенный** процент скидки СПП на конкретный товар, обычно ~20–25%.
- Реальная скидка от карточки за неделю получается выше (32,9% для этой недели), потому что в R14 владелица **вычитает возвраты**, а ещё работает накопительная скидка покупателя.
- **Правильная формула «по карточке» = `SUM(retail_price × quantity) для Продаж − SUM(retail_amount) для Возвратов`**, НЕ `retail_amount × (1 + spp_prc/100)`.

## 2. Перезалив исторических данных в WB API

- WB Statistics API отдаёт полную детализацию (storage_fee, acquiring_fee, spp_prc и т.д.) за весь 2025 год.
- Edge function упирается в wall-clock таймаут при периодах > ~3 месяцев.
- **Рабочая стратегия:** месячные чанки, **не более 2 параллельных запросов** (3+ ловят WB rate limit 429 и DB statement timeout).
- Идемпотентный UPSERT по `rrd_id` — повторный прогон безопасен.
- Запуск из SQL: `SELECT net.http_post(url, headers, body, timeout_milliseconds := 120000)`.

## 3. Воронка продаж — общая основа для нескольких модулей

Таблица `wb_sales_funnel` (показы / клики / в корзину / заказы / выкупы / возвраты / оборачиваемость) — **переиспользуется**:

- **% выкупа** — для дашборда и колонок в аналитике
- **Оборачиваемость** — для решения об участии в акциях
- **Реклама** — расчёт CPC, CPM, конверсий по этапам, ROAS, ДРР (CR показы→клики, клики→корзина, корзина→заказ, заказ→выкуп)
- **Лайфсайклы товаров** — детект «застрял на этапе» (много показов, мало кликов = плохое фото; много кликов, мало заказов = плохая цена/описание)

**Источник:** WB API «Воронка продаж» (точный endpoint в процессе ресёрча, ежедневный cron).

## 4. Источники данных — только автоматика + одно ручное поле

**Принцип:** все метрики (% выкупа, оборачиваемость, маржа, комиссия, логистика, хранение, СПП, заказы, выкупы, возвраты, конверсии) — **автоматически из WB API**. Ничего ручного, кроме одного.

**Единственное ручное поле:** `sku_catalog.cost_price_rub` = «Себестоимость до ВБ» из UNIT.xlsx [лист Юнит, колонка 6].

Это значение **уже включает**:
- закупочную цену в Китае
- карго до РФ
- индивидуальную обработку / упаковку
- доставку до склада WB

Отдельных полей «фулфилмент» / «доставка до складов» **не заводить** — они часть «Себестоимости до ВБ».

Обновление `cost_price_rub` — только из UNIT.xlsx загрузкой (не ручным вводом в UI), источник фиксируется в `cost_price_source`.

### Перспектива (ROADMAP): автоматический расчёт себеса

Сейчас `cost_price_rub` = вручную внесённая «Себестоимость до ВБ». В перспективе разложить её на компоненты, чтобы расчёт был автоматическим:

```
Себестоимость на ед. = Закуп Китай + Карго + Фулфилмент + Доставка до склада WB
```

Источники данных (у владелицы уже есть Excel-таблицы по этим темам):
- **Заказы в Китай** — закупочная цена + объём партии → формирует closure_price_per_unit
- **Поставки** — транспортные расходы (карго, транзит) → разносятся пропорционально на единицу
- **Фулфилмент (ФФ)** — расходы на ед. (приёмка, переупаковка, инд. обработка)
- **Доставка до склада WB** — платная, привязана к поставке

Когда модули заведутся:
- Новые таблицы: `china_orders` (уже есть), `china_order_items`, `supplies` (уже есть), `fulfillment_costs`, `delivery_to_wb`
- View `v_sku_cost_breakdown` — собирает себес из этих 4 источников по nm_id
- `sku_catalog.cost_price_rub` остаётся как «факт сейчас», но может пересчитываться скриптом из view

Это **обширный и важный** блок, отдельная задача. Сейчас просто фиксируем перспективу.

## 5. Промо-акции WB — модель данных и решения

- **Несколько параллельных акций:** каждая пара (`promotion_id × nm_id`) — отдельная строка в `wb_promotion_items`. Финальная цена на витрине = `MIN(plan_price)` среди акций, где `user_participate = true`.
- **Решение пользователя:** колонки `user_participate BOOL`, `user_decided_at`, `user_note` в `wb_promotion_items`. NULL = ещё не решено.
- **Оборачиваемость = дни до распродажи стока.** Формула: `остатки на сегодня / средние продажи в день за последние 28 дней`. **Чем больше дней — тем хуже** (товар залёживается).
- **Границы оборачиваемости (для рекомендации участия в акции):**
  - **< 60 дней** — товар продаётся хорошо, акция не нужна (рекомендация по марже)
  - **60–90 дней** — акция полезна для ускорения распродажи
  - **> 90 дней** — срочно сливать, акция нужна даже при минусовой марже
- **Авто-акции (`type=auto`):** WB сам назначает скидку, выйти из API нельзя — только в ЛК. Эндпоинт `nomenclatures?inAction=true` возвращает текущий список SKU; `inAction=false` отдаёт 422.
- **Rate limit WB Promo API:** 10 req/мин, global limiter per seller. Между вызовами `nomenclatures` держать ≥2,5 с.

## 6. Секреты Supabase

> **⚠️ ВАЖНО для AI: `WB_TOKEN_READ` — единый токен на ЧТЕНИЕ всех параметров (Статистика, Цены и скидки, Контент, Аналитика, Маркетплейс, Финансы, Продвижение). У владелицы выпущен ОДИН такой токен, его достаточно для любой нашей edge function.**
>
> **При 401 / `Access token withdrawn` от WB:**
> - НЕ просить владелицу зайти в кабинет / обновить Secret / выпустить новый токен.
> - НЕ предлагать «вручную проверить токен», «обновить GitHub Secret», «передеплоить функцию».
> - Считать что владелица обновляет токен сама когда узнаёт что он отозван — это её зона ответственности, не пользовательская задача от ИИ.
> - Зафиксировать ошибку в `ingestion_log`, сообщить факт («WB API возвращает 401 с N такого-то дня, код-часть исправна») один раз и не возвращаться к теме.
>
> **Любые попытки записывать через WB API (upload, change price, и т.п.) — НЕ работают**, токен это не позволит. В будущем для записи понадобится отдельный токен.

- Один токен для всех WB-функций: **`WB_TOKEN_READ`** (read-only, все категории).
- Старое имя `WB_API_TOKEN` оставлено как fallback в коде (`Deno.env.get("WB_TOKEN_READ") ?? Deno.env.get("WB_API_TOKEN")`), но в env его держать не нужно.

## 7. UI: одна страница — одна ширина

**Правило:** любая страница, таблица, график должны умещаться в ширину экрана без горизонтального скролла, если данные физически это позволяют.

**Что это значит на практике:**
- Если колонок таблицы много — пересмотри, какие реально нужны (бренд, доп. идентификаторы и т.п. убирай если они дублируют title/категорию)
- Длинные подписи сокращай и переноси на tooltip (`Видимость / Доверие / Ценность` → `В/Д/Ц` с расшифровкой при наведении)
- Прогресс-бары и multi-line ячейки сжимай до 1 строки если возможно
- Графики: используй адаптивные viewBox/PAD, не фиксированный пиксельный max-width
- Перед добавлением новой колонки/блока — спросить себя «помещается на 1366×768 без скролла?»

**Когда горизонтальный скролл всё-таки оправдан:**
- Сравнительные таблицы где ВСЕ колонки обязательны (P&L по статьям × 10+ статей)
- Wide-screen аналитика которая не имеет смысла на узком экране

В этих случаях оборачивать в `overflow-x-auto` внутри карточки (не наружу страницы), чтобы скроллилась только таблица, а не весь viewport.

## 8. Период по умолчанию — 30 дней

**Правило:** все агрегации, метрики, KPI и аналитика по умолчанию считаются за **последние 30 дней**, если в UI нет явного селектора периода.

**Где применяется:**
- Воронка продаж (open / cart / order / buyout)
- Конверсии, % выкупа, рейтинги
- Топ-5 товаров, категории
- Любые карточки с дельтой «за месяц»

**Исключение:** расчёт поставок и прогноз запасов — там окно исходных данных оговаривается отдельно для каждой задачи (типично 60-90 дней для стабильности прогноза).

**Почему 30:**
- Совпадает с тем что показывает WB-кабинет (точка опоры для владелицы).
- На длинных окнах метрики «размываются» — пользователь не видит свежих изменений.
- Для дельт «за месяц» нужен предыдущий месяц как база.

**Если окно агрегации в БД больше (например `wb_sales_funnel_period` = 60 дней):**
- Краткосрочно: в UI показывать с пометкой «за окно фетча», объяснить что период фетча > 30.
- Долгосрочно: задача в backlog — поменять параметр в edge function на 30 дней + перезалить.

## 9. Живой TODO + автономная работа

**Правило:**

1. **Каждый фикс/баг/правка от пользователя → сразу в TODO-список** (`tasks/ITERATION_PLAN.md` или эквивалент в проекте). Не держать в голове, не пропускать. Формат — чекбокс `- [ ]` с коротким описанием.

2. **Если пользователь молчит → беру следующий пункт из TODO и делаю сам.** Без вопросов «продолжить?» если задача чёткая и в моей компетенции (код, миграции, query, UI). Молчание ≠ остановка.

3. **При возвращении пользователя — сначала отчёт.** Перед новой задачей: «пока тебя не было, сделал A, B, C; в работе D; жду E». Только потом — следующий шаг.

**Что НЕ делаю автономно:**
- Деструктивные действия (drop tables, force push, mass update БД).
- Архитектурные решения без согласования (новая схема, новый сервис).
- Внешние коммуникации (комментарии в чужих PR, посты).

**Где исключения:** если в задаче из TODO явно стоит флаг «спросить пользователя» — спрашиваю.

## 10. Полная цепочка push → main (zero-touch для пользователя)

**Принцип:** пользователь не должен ловить технические баги (build failed, lint, types, unused, missing PR, отстающий main). Я довожу каждый push до **READY в main** сам.

### Цикл после любого commit

```
edit → mental-check → commit → push → присылаю PR ссылку → жду CI → проверяю build → fix если ERROR → ждать merge → проверяю main
```

### Шаги

**1. Перед `git commit` — mental check:**
- Удалил ли неиспользуемые импорты? (`ChannelsDonut`, `Badge`, `CardTitle`, ...)
- Удалил ли неиспользуемые переменные? (`channels`, `deltaYesterday`, `fmt`, ...)
- Нет ли висящего `<<<<<<< HEAD` после merge?
- Все ли helper-функции реально вызываются? (если объявил `fillHours`, `DeltaPill` — использую их или удаляю).

**2. После `git push`:**
- **Проверить открыт ли PR с этой ветки в main.** Если нет → `mcp__github__create_pull_request(base='main', head='<ветка>', draft=false)`.
- **Сразу прислать ссылку PR пользователю в чат** (`https://github.com/owner/repo/pull/NNN`).

**3. Через 30-60 секунд после push (CI стартует):**
- `mcp__Vercel__list_deployments` — найти свежий deployment с моим SHA.
- Если `state=BUILDING` → ждать ещё 1-2 минуты.
- Если `state=ERROR` → `get_deployment_build_logs` → найти причину → fix → goto шаг 1.
- Если `state=READY` → ✅ можно идти к следующей задаче.

**4. После того как пользователь смержит PR:**
- `pull_request_read` → проверить `merged=true`.
- `git fetch origin main && git log origin/main -1` → проверить что новый коммит в main.
- Если на ветке появятся новые коммиты позже — **сразу открыть следующий PR** (GitHub не делает это автоматически после squash-мержа).

### Что пользователь НЕ должен ловить
- Build failed (ESLint, типы, missing import)
- «main не обновляется» (значит я не открыл PR)
- «PR отсутствует» (создаю сразу после push)
- Merge conflicts (резолвлю сам, не показываю)
- Vercel ERROR деплои в истории (фикшу до того как пользователь увидит)

### Что пользователь МОЖЕТ ловить
- Функциональные баги: логика, UI, цифры, формулы, расположение блоков, тексты.
- Архитектурные вопросы: «правильно ли так делать?».
- Новые задачи и фиксы.

## 11. Делегирование агентам — основной режим работы

**Правило:** моя роль — архитектор и приёмщик, а не исполнитель.

**Что делаю Я:**
1. **Принимаю решение** что и как делать (формула P&L, схема таблицы, структура компонента, расположение блоков).
2. **Пишу чёткий план** для агента: какие файлы тронуть, что именно изменить, как проверить.
3. **Принимаю работу:** читаю diff, проверяю что сделано, мержу или возвращаю на исправление.

**Что делает АГЕНТ:**
- Реализация: написать компонент, query, миграцию, тесты.
- Поиск по репо, чтение больших файлов.
- Параллельные независимые задачи (например, два разных компонента одновременно).

**Когда сам пишу:**
- Тривиальные правки 1-3 строк (быстрее самому).
- Когда задача требует контекста сессии, который сложно передать.
- Архитектурные миграции (когда формула P&L — не очевидно).

**Доступные агенты:**
- `general-purpose` — для написания кода, исследования, многошаговых задач
- `Explore` — read-only поиск кода
- `claude-code-guide` — про Claude Code/SDK/API

**Правило параллелизма:** если независимых задач 2+ — запускаю агентов одной сессией (multiple Agent tool calls in one message) → ждать результат → собрать в один коммит.

## 11a. Выбор модели для агента

**Дефолт: `sonnet`** (general-purpose) — 90% задач: компонент, query, миграция, тесты, рефакторинг.

**`haiku`** — тривиал: поиск файлов, чтение, простые правки 1-3 строки. Дёшево + быстро.

**`opus`** — только: архитектура новой системы, сложный дебаг, BIG-задачи требующие глубокого reasoning. Дорого, в работе использовать редко.

**Правило:** не запускать `opus` без явной необходимости. Sonnet справится с подавляющим большинством — её и используем по умолчанию.

## 13. Расширение автономии (2026-06-15)

**Можно самостоятельно (без спроса):**

1. **Самостоятельный поиск багов** — регулярно запускать UAT-агентов на страницы/компоненты, фиксировать находки в `todo.md`.
2. **Фиксить баги, найденные при UAT** — без отдельного согласования. Сразу делегировать починку агенту.
3. **Принимать решения о компактных рефакторингах** — пагинация/виртуализация/дебаунс/индексы/обновление зависимостей с понятным upside. До 1 файла — сам. Большие touch'и (>5 файлов / архитектура) — спрашивать.
4. **Запускать `migrate.yml`** через `workflow_dispatch` когда нужно применить миграции — без подтверждения.
5. **Мержить PR самостоятельно** через `mcp__github__merge_pull_request` (squash) — но **в правильном порядке**, чтобы PR от агентов не обгоняли друг друга:
   - Сначала мерж PR где меньше всего конфликтов (старые → новые).
   - Если PR-Б был открыт после PR-А и зависит от него — сначала PR-А, потом ребейзить PR-Б.
   - После каждого мержа — `git fetch origin main` локально, чтобы не отстать.

**По-прежнему спрашиваю:**
- Архитектурные решения (новая схема БД, новый сервис, смена формулы P&L)
- Деструктивные действия (drop tables, force push, mass UPDATE)
- Внешние коммуникации (комментарии в чужих PR, посты, email)
- Большие фичи с >1 разумным путём
- Когда нашёл много багов (>5) и нужен приоритет

## 14. Один пункт → до зелёного мержа → следующий

**Правило:** беру **только один** пункт из todo за раз. Цикл:

```
1. Взять пункт → сделать (сам или через агента)
2. Commit → push → авто-открытый PR
3. Дождаться CI зелёного (если ERROR — fix)
4. MERGE в main через mcp__github__merge_pull_request (squash)
5. Обновить tasks/todo.md (закрыть пункт)
6. Только теперь брать следующий пункт
```

Не накапливать висящие PR. Не браться за второе дело до того как закрыто первое.

### Параллельные агенты — когда можно, когда нельзя

**МОЖНО** параллелить если:
- Задачи затрагивают **РАЗНЫЕ файлы** (агент A пишет компонент X в `features/foo/`, агент B пишет миграцию в `supabase/migrations/`)
- В брифе агенту явно указано «трогать только эти файлы»

**НЕЛЬЗЯ** параллелить если:
- Одни и те же файлы (page.tsx, общий типы, общая query)
- Один пункт зависит от другого (агент B использует функцию которую делает агент A)

**Если очень нужны 2 пересекающиеся задачи** — выполнять **последовательно**: запустить агента A → дождаться → commit + push → потом агента B.

### Дисциплина при чехарде

Если уже накопились 5+ PR от агентов и они конфликтуют:
1. Закрыть все кроме самого первого, ничего не мерж'я
2. Тот первый довести до мержа
3. Сделать `git fetch origin main` + `git merge origin/main` на ветке
4. Один за другим перезапустить остальных, **меняя scope** чтобы не пересекались.

## §15 Автономная зачистка после аудита (железобетонно)

**Правило:** после генерации `docs/AUDIT_*.md` я работаю **автономно без новых тычков** пока:
- Все 🔴 КРИТИЧНО — решены или явно отложены владелицей с её решением
- Все 🟠 СЕРЬЁЗНО — решены если безопасные (без потери данных, без сноса прод-функциональности) либо явно эскалированы с альтернативой
- Все 🟡 СТОИТ ПОФИКСИТЬ — закрыты (это всегда безопасные мелкие)
- Все 💡 МОЖНО УПРОСТИТЬ — выполнены если безопасные

**Зона моей автономии:**
- Удаление мёртвого кода (после grep подтверждения что не используется)
- Удаление дубликатов файлов/миграций
- Рефакторинг под `_shared/` без изменения семантики
- Подключение существующих unused тестов к CI
- Параллелизация чисто читающих запросов
- Подстановка констант из `business-rules.ts` вместо магических чисел
- Добавление advisory locks / индексов БД (через миграции)
- Включение `verify_jwt = true` если есть рабочая альтернатива доступа

**Стоп-сигналы (только эти 3 случая жду решения):**
1. Удаление прод-данных или таблиц с пользовательскими записями
2. Изменение бизнес-формулы (P&L, маржа, выкуп — то что владелица сверяет с Excel)
3. Архитектурное решение между несколькими равноценными путями (например: Auth через Supabase Auth vs shared secret vs JWT — выбор делает владелица)

**Что делаю при стоп-сигнале:**
- НЕ жду пассивно
- Записываю в `tasks/todo.md` секцию «⏸ Требует решения владелицы» с конкретными альтернативами и рекомендацией
- Беру следующий пункт аудита и продолжаю
- Не возвращаюсь к этой задаче пока не получу ответ

**Метрика готовности:** после каждой сессии в `docs/AUDIT_*.md` дописываю под каждым пунктом одну из меток: ✅ закрыто / ⏸ ждёт решения / 🔄 в работе / ❌ невозможно технически.

## §16 Замена `.range(0, X)` на RPC агрегацию — обязательная сверка

**Правило:** при переписывании любого запроса `supabase.from(...).range(0, N)` где N ≥ 50_000 (то есть «тянем сырьё в Node для агрегации в JS») на серверную RPC:

1. **До коммита** — через `mcp__Supabase__execute_sql` вызвать ОБЕ версии параллельно:
   - старая JS-логика воспроизводится в SQL (`SELECT ... + WHERE filters + sum/count в SQL аналогом JS reduce`)
   - новая RPC через `SELECT ... FROM public.get_xxx(...)`
2. Сравнить ключевые цифры (count, sum, distinct count и т.п.). **Идентичность — условие коммита.**
3. **Если расходятся — НЕ коммитить.** Записать диагноз: старое значение, новое значение, гипотеза причины (округление, NULL-обработка, фильтр). Эскалировать владелице.
4. В commit body — **обязательно** строка «Сверка через MCP execute_sql: X ✓» с конкретными числами обеих версий.

**Почему:** у `wb_reports_fact` нет автотестов формул. JS reduce и SQL агрегаты могут разойтись на:
- NULL-обработке (`COALESCE(x, 0)` vs `toNumber(x)`)
- Порядке округления (`Math.round` per-row vs after-sum)
- Типах (numeric vs float vs string-from-postgres)
- Семантике `quantity > 0` (возвраты vs продажи)

**Образец паттерна:** PR #147 (data-quality) — RPC `get_channel_gap_dates`, сверка `wb_sales 13/wb_reports 25 distinct days`. Полная цепочка: миграция через `mcp__Supabase__apply_migration` → сверка через `execute_sql` → правка TS → `tsc/eslint/build` → коммит → push → авто-PR.

**Правило миграции (схема):** каждая RPC — `SECURITY INVOKER`, `SET search_path = ''`, `STABLE`, `LANGUAGE sql`, явный `GRANT EXECUTE ... TO authenticated, service_role`, `COMMENT ON FUNCTION ... IS '...замена .range(...) в <file>'`.

_Источник: SellerBase 2026-06-21 — рефакторинг 9 файлов из аудита 2026-06-20 без регрессий благодаря этому циклу._

## §17 Карточки товаров — весь контур в SellerBase (2026-08-20)

**Правило:** всё, что касается карточек товаров и действий с ними, ведётся в этом репозитории.
Никаких «файлов на стороне» и знаний, которые живут только в переписке.

**Что сюда входит.** Два раздела: `docs/seo/` — тексты и продвижение,
`docs/marking/` — классификация и «Честный ЗНАК». Смешивать их не нужно, это разные предметы.


| Область | Где лежит |
|---|---|
| **Точка входа в контур карточек** | **`docs/seo/README.md`** |
| Алгоритмы SEO площадок, правила описаний | `docs/SEO_MARKETPLACES.md` |
| Словарь стоп-слов | `docs/seo/stop-words.md` |
| SQL-сканер карточек | `docs/seo/scan-stop-words.sql` |
| Коды ТН ВЭД / ОКПД 2 и маркировка ЧЗ по группам | `docs/marking/codes-marking.md` |
| Данные карточек | Supabase `public.sku_catalog` |
| Готовые описания | `docs/seo/descriptions/<группа>.md` |
| Правки в кабинете (наименования, характеристики) | `docs/seo/checklist-kabinet.md` |

**Порядок работы:**

1. Любая новая находка по карточкам — сразу в соответствующий файл, а не в чат.
2. Изменения в описаниях сначала фиксируются в репозитории, потом заливаются в кабинет.
3. После каждой пересборки описаний — прогон сканера из `docs/seo/scan-stop-words.sql`
   и обновление словаря, если появились новые формулировки.
4. Excel-выгрузки считаются производными артефактами: источник истины — markdown и SQL в репо.

**Почему:** карточек 80+, правок по ним больше сотни, а знание про алгоритмы площадок
устаревает и требует датировки. Без единого места это расползается по чатам и файлам,
и следующая сессия начинает с нуля.
