## 1. Что такое SellerBase

Data-платформа для управления бизнесом на маркетплейсах. Заменяет Excel-комплекс (UNIT, ПОСТАВКА, CF/PL).

- MVP: только Wildberries.
- Стек: Supabase (PostgreSQL + Edge Functions + Auth) + Lovable (frontend) + Vercel (deploy).
- Соло-проект: один владелец, минимум boilerplate, максимум прозрачности.

---

## 2. Архитектурные принципы (фундамент надёжности)

Подробно — в `docs/PLAN.md` раздел «Принципы надёжности и расширяемости». Ключевое:

1. **Сырые данные отдельно от расчётных** (`*_raw` JSON неизменно → нормализатор → `*_fact`).
2. **Idempotent UPSERT** по бизнес-ключу — cron можно гонять сколько угодно раз.
3. **`ingestion_log`** — каждый запуск фетчера пишет статус, можно увидеть здоровье системы за минуту.
4. **Расчёты — только VIEW**, не таблицы. Поправил формулу = пересчиталось всё.
5. **Декомпозиция view** сверху вниз — сломалась маленькая, большая отдаст «нет данных», а не неверные цифры.
6. **`v_data_quality`** — sanity checks как view, ошибка не уйдёт молча.
7. **`app_settings`** (key/value) — все внутренние коэффициенты. WB-комиссии берутся пер-артикул из отчёта, не из настроек.
8. **История** у всего что меняется (`cogs_history`, `wb_tariffs_*_history`).
9. **Расширение только через добавление**, не переписывание.
10. **Edge Functions ловят ошибки в `ingestion_log`** и не падают с пустыми руками.

## 4. Классификация задач

### SMALL — делать сразу
- Правка 1–3 файлов
- Новая view (расчёт)
- Новый ключ в `app_settings`
- Документация

### BIG — спросить перед реализацией
- Новая таблица (миграция)
- Изменение публичного контракта Edge Function
- Удаление файлов/функций
- Задача занимает >10 минут или >2 слоёв (БД + код)

Для BIG — сначала план, реализация после подтверждения.

## 5. Стиль общения

- Русский в чате, английский в коде
- Конкретно, без воды
- Уточняющие вопросы перед BIG-задачами
- Не придумывать scope сверх запроса
- Комментарии в коде — только когда WHY неочевиден

---

## 6. Принципы работы с кодом

- Не добавлять фичи без запроса
- Не рефакторить «заодно»
- Не создавать абстракции под гипотетическое будущее
- Простой код лучше «правильного»
- Verification: перед «готово» — sanity-check через `v_data_quality` или ручной SQL
- Безопасность: zod на входы Edge Functions, RLS на таблицы, никаких service_role во фронте

- Разработка на `claude/...` ветках

- `automerge.yml` мержит squash'ем

## 8. Журнал сессий

`tasks/SESSION_LOG.md` — записываем итог каждой рабочей сессии. Append-only, новые записи сверху.

**Что пишем в запись:**
- Дата и цель сессии.
- Решения, принятые в этой сессии (архитектура, scope, выбор инструментов).
- Что сделано (миграции, PR, view, фетчеры).
- Состояние внешних систем (Supabase advisors, GitHub Secrets).
- Что ждёт владельца (токены, решения).
- Следующие шаги.
- Незакрытые вопросы.
- Ограничения среды.

**Когда пишем:**
- В конце сессии (см. CLAUDE.md «Конец сессии»).
- При крупных промежуточных вехах (конец фазы, перед долгой паузой).
