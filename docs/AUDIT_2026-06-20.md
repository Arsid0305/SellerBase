## Резюме (краткое)

Проект технически здоров: `tsc --noEmit`, `eslint .` и `next build` проходят чисто без единой ошибки. Основные риски — не в синтаксисе, а в архитектурном дрейфе и незакрытых пунктах прошлого аудита (17.06): auth на API всё ещё практически отсутствует (новый middleware проверяет только Origin/Referer, что не защищает от ботов и curl), все 16 edge functions публично вызываемы без JWT, а раздвоение `margin-analyzer` v1/v2 усугубилось — теперь это два параллельных продакшен-маршрута с разными формулами маржи (v2 даже не вычитает налог). Производительность (`.range(0, 200_000)` + ин-мемори агрегация) и нулевое покрытие unit-тестами остаются не тронутыми с прошлой сессии.

## 🔴 КРИТИЧНО (требует немедленного действия — баги, дыры)

- **`middleware.ts` создаёт ложное чувство защищённости API.** `apps/web/src/middleware.ts:13-23` пропускает все non-GET запросы, у которых `Origin`/`Referer` совпадает со списком хостов. Эти заголовки полностью контролируются клиентом — любой `curl -H "Origin: https://seller-base.vercel.app"` или серверный бот проходит проверку. Это не аутентификация, а фильтр от случайного браузерного CSRF. Все 27 `app/api/**` ручек (costs, demo/clear, personas, scenarios, goals, suppliers, supplies, …) по факту так же открыты внешнему вызывающему, как и было на 17.06 — просто теперь выглядит как «исправлено». **Рекомендация:** добавить проверку Supabase Auth session (`supabase.auth.getUser()`) в middleware или в каждый route handler, Origin-проверку оставить как доп. слой, не основной.

- **Все 16 edge functions имеют `verify_jwt = false` — регресс относительно прошлого аудита.** `supabase/config.toml` — на 17.06 было отмечено 4-7 функций без JWT, сейчас абсолютно все: `fetch-wb-stocks`, `fetch-wb-funnel`, `fetch-wb-funnel-aggregate`, `fetch-wb-promotions`, `fetch-wb-tariffs`, `fetch-wb-report`, `fetch-wb-content`, `fetch-wb-sales`, `fetch-wb-goods-returns`, `fetch-wb-commissions`, `fetch-wb-orders`, `detect-anomalies`, `fetch-wb-ads`, `telegram-alerts`, `sync-sheets`, `send-notification`, `telegram-webhook`. Комментарии вида «pg_cron внутри Supabase — JWT не нужен» — логическая ошибка: `verify_jwt=false` не ограничивает вызывающего pg_cron'ом, оно убирает требование JWT для **всех**, включая внешних. Любой, кто узнает публичный URL функции (легко найти по паттерну `https://<project>.supabase.co/functions/v1/fetch-wb-sales`), может вызывать её произвольно: тратить WB API rate-limit чужого токена, плодить дублирующиеся `ingestion_log` записи, преждевременно ротировать `wb_orders_fact`/`wb_sales_fact`. **Рекомендация:** включить `verify_jwt = true` везде и вызывать из pg_cron через `service_role` JWT (стандартный паттерн Supabase), либо добавить секретный shared-token header и проверять его в каждой функции.

- **Нет защиты от конкурентных запусков cron-функций → объясняет «зомби» записи из прошлого аудита.** `supabase/functions/_shared/ingestion.ts` (`runJob`) пишет статус `running`→`ok`/`error`, но не проверяет, есть ли уже активный запуск с тем же `job_name`, и не использует `pg_try_advisory_lock`. Если запуск зависает (таймаут Edge Function, сетевой сбой к WB API), следующий запуск по cron (через 30 мин для `fetch-wb-sales`/`fetch-wb-orders`) стартует параллельно — гонка на upsert в `wb_sales_fact`/`wb_orders_fact`, а первая запись навечно остаётся в статусе `running`, что глушит мониторинг (Telegram-алерт по статусу не сработает, т.к. ждёт `error`, а тут вечный `running`). Это и есть причина уже зафиксированного в прошлом аудите факта «`fetch-wb-sales-30min` ❌ зависшие записи running с 14.06» — то есть проблема не точечная, а системная, и до сих пор не исправлена. **Рекомендация:** добавить в `runJob` проверку `SELECT 1 FROM ingestion_log WHERE job_name=$1 AND status='running' AND started_at > now() - interval '1 hour'` перед стартом, либо `pg_try_advisory_lock(hashtext(job_name))`.

- **`china_orders.cny_rate` — мёртвое поле, формирующее ложные ожидания у пользователя.** UI (`features/costs/costs-explorer.tsx:302`) даёт ввести курс юаня при импорте партии («Заказ Китай»), значение сохраняется в `china_orders.cny_rate` (`app/api/import/china-order/route.ts:60`). Но реальный расчёт себестоимости в `calculate_cogs_for_shipment` (`supabase/migrations/0007_calculate_cogs_function.sql:20,54`) берёт курс исключительно из `cargo_shipments.exchange_rate` (который сам берётся из отдельной таблицы `cargo_tariffs.cny_rate_rub`). Введённый пользователем курс конкретного заказа **никогда не читается** ни одним запросом в кодовой базе (проверено `grep` по всему `apps/web/src` и `supabase/migrations`) — себестоимость считается по текущему общему курсу, а не по курсу на момент конкретной закупки. Если владелица меняет курс между заказами, ожидая, что «вот этот заказ считается по своему курсу», расчёт это игнорирует. **Рекомендация:** либо использовать `china_orders.cny_rate` как override в `calculate_cogs_for_shipment` (через `cargo_shipment_orders` → `china_orders`), либо убрать поле ввода из UI, чтобы не создавать иллюзию контроля.

При росте данных (>200k строк фактов) — тихий обрыв данных без ошибки (Supabase просто не вернёт лишнее) и деградация RSC-рендера. **Рекомендация:** перенести агрегацию в RPC/materialized view по образцу `v_margin_breakdown_weekly` или `get_full_pnl_by_period` — паттерн в кодовой базе уже есть, не везде применён.

- **Дублирующиеся миграции — 3 пары идентичных файлов в репо.** Побайтово совпадают (проверено `md5sum`):
  - `20260618000003_unschedule_old_fetch_wb_content_daily.sql` ≡ `20260618_unschedule_old_fetch_wb_content_daily.sql`
  - `20260618000004_wb_sales_fact_enable_rls.sql` ≡ `20260618_wb_sales_fact_enable_rls.sql`
  - `20260618000005_close_previous_cost_search_path.sql` ≡ `20260618_close_previous_cost_search_path.sql`

  Не критично для прода (Supabase отслеживает применённые миграции по имени файла, так что обе версии каждой пары были применены как «разные» миграции — `ALTER VIEW ... Создаёт путаницу при чтении истории и риск, что будущий разработчик случайно подумает, что это две разные правки. **Рекомендация:** при следующей пересборке миграционной истории — оставить только timestamped-версии (`200600xxxx`), legacy-формат (`20260618_*` без часов) исключить из новых коммитов.

- **`fetch-wb-sales` и `fetch-wb-orders` — ~70% идентичного кода без общего хелпера.** Сравнение diff показывает совпадающую структуру: парсинг `x-ratelimit-retry` заголовка, backoff `(retry + 1) * 1000`, пагинация через `lastChangeDate`, dedup по Set, `runJob` wrapper — отличается только маппинг полей и upsert-таблица. `fetch-wb-ads/index.ts:117-123` независимо реализует тот же retry-паттерн третий раз. **Рекомендация:** вынести в `supabase/functions/_shared/wb-client.ts`: `fetchWbPage(url, token)` с встроенным rate-limit retry, и `paginateByLastChangeDate(fetchPage, dedupKey)` — сократит каждую из трёх функций на 40-60 строк и унифицирует поведение при 429.

## 🏗️ Архитектурные предложения (стратегические — требуют решения владелицы)

1. **Слой `entities/*` vs `features/*` — границы соблюдены аккуратно** в проверенных модулях (`entities/*/queries.ts` — чистый доступ к данным, `features/*/...-client.tsx` — UI с `'use client'`). Единственное реальное нарушение масштаба — дублирование целого вертикального слайса (margin-analyzer v1/v2) вместо эволюции одного. Рекомендация: при следующей «v2»-итерации любой фичи — переименовывать/заменять оригинал, а не создавать параллельную папку, иначе риск повторения этой же ситуации (как уже произошло однажды).

2. **Подключение auth — решение масштаба, а не патча.** Сейчас «один пользователь» — это осознанный риск, принятый владелицей согласно прошлому аудиту. Но `verify_jwt=false` на всех edge functions — это не «один пользователь использует свою БД», это «весь интернет может вызвать функции, которые тратят чужой WB API rate-limit и пишут в БД». Разница существенная: API routes без auth — это риск для *владелицы* (кто-то испортит её данные), edge functions без JWT — риск для *стабильности интеграции с WB* (есть нефиксированный потолок запросов в день у WB API, его может исчерпать кто угодно).

3. **Unit-тестирование финансовых формул — без изменений с 17.06, риск растёт пропорционально количеству правок маржи/P&L.** За последнюю неделю в `margin-analyzer-v2` появилась независимая (и менее корректная) реализация маржи именно потому, что не было теста, который заставил бы заметить расхождение с v1. Это прямая иллюстрация стоимости отсутствия тестов, а не абстрактная рекомендация.
