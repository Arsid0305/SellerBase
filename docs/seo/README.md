## 1. Три места, где живут карточки

Разделение важно: путаница между ними — главный источник потерянной работы.

| Где | Что там | Кто меняет |
|---|---|---|
| **Репозиторий** | тексты, правила, находки, чеклисты | человек и ИИ, через PR |
| **Supabase**, `public.sku_catalog` | текущее состояние карточек WB: наименование, описание, характеристики, габариты | `fetch-wb-content` тянет из WB |
| **Supabase**, `public.ozon_content` | то же по Ozon: название, описание, характеристики, фото, габариты | `fetch-ozon-content` тянет из Ozon |
| **Кабинет WB** | то, что видит покупатель на WB | только человек, руками |
| **Кабинет Ozon** | то, что видит покупатель на Ozon | только человек, руками |

**Направление одно:** репозиторий → кабинет → база. Тексты правятся в файлах, заливаются
в кабинет, оттуда попадают в базу при следующем прогоне `fetch-wb-content`. Обратного
пути нет: правка сразу в кабинете теряется для следующей сессии, потому что источник
истины по текстам — файлы, а не карточка.

**Это единственная точка входа в раздел** (правило — `../../tasks/rules.md` §26).
Новый файл в `docs/seo/` называется здесь строкой в том же коммите: файла, которого
нет в этой карте, для следующей сессии не существует.

├── seo/                       ← ТЕКСТЫ И ПРОДВИЖЕНИЕ
│   ├── README.md              ← этот файл: карта, порядок действий, инструменты
│   ├── card-assembly.md       ← РЕГЛАМЕНТ пересборки: 4 фазы, источники, перебор полей

│   │   ├── README.md          ← таблица групп, статус, порядок заливки

│   ├── stop-words.md          ← словарь: 🔴 / 🟠 / 🟢 и чем заменять
│   ├── measurement.md         ← чем мерить эффект правок, когда позиций нет
│   ├── scan-stop-words.sql    ← два SQL-сканера: по текстам и по характеристикам
│   ├── infographics/          ← задания на слайды и видео, 4 группы
│   │                             ⚠️ разбор отложен решением владелицы 03.09, не трогать
│   └── СПРАВОЧНИКИ (json, машиночитаемые — их читают скрипты)
│       ├── cabinet-live.json      ← слепок кабинета из API продавца, 67 карточек.
│       │                             ПРИОРИТЕТНЕЕ cabinet-export.json при расхождении
│       ├── cabinet-export.json    ← ручная выгрузка кабинета, старше и полнее по полям
│       ├── discontinued.json      ← 9 артикулов, выведенных из продажи: в книгу не идут
│       ├── catalog-facts.json     ← факты по SKU: цвет, размер, состав группы
│       ├── packaging.json         ← габариты предмета и упаковки, вес нетто
│       └── unit-weights.json      ← веса и габариты из юнит-экономики владелицы

`seo/` и `marking/` намеренно разделены: это разные предметы. Первый — про то, как карточку
находят и покупают. Второй — про то, к какой товарной группе она относится и что за это
следует по закону. Пересекаются они в одном месте — в формулировках, см. §4.

**Два слепка кабинета — не дубль.** `cabinet-live.json` тянется из API продавца и всегда
свежее; `cabinet-export.json` — ручная выгрузка, в ней есть поля, которых API не отдаёт.
При расхождении верен `cabinet-live.json` (`../../tasks/rules.md` §22).

**Соседнее в репозитории, что стоит знать:** `tasks/rules.md` — правила проекта (§17 про
карточки, §18–§26 — правила разбора и текста), `tasks/SESSION_LOG.md` — журнал сессий,
`tasks/todo.md` — текущие задачи, `tasks/excel-from-owner/` — книги владелицы, из которых
берутся веса и себестоимость, `supabase/` — миграции и Edge Functions, включая
`fetch-wb-content`.

## 3. Как действовать: заливка пересобранных карточек

### Шаг 0. Смержить PR

Тексты приходят в `main` только через PR. Actions на аккаунте отключены с июля 2026 —
`automerge.yml` не сработает, мержить руками. Пока PR открыт, в `main` файлов нет.

### Шаг 1. Сначала риск, потом всё остальное

`checklist-kabinet.md`, **раздел A** — девять пунктов. Это не про SEO, это про
классификацию и маркировку.

Первым идёт `AAND1ST202BL`: «зубная щётка» стоит в трёх полях — наименование,
«Особенности товара для животных», «Комплектация». Позиция 9603 21, маркировка
обязательна с 01.10.2026. Пока формулировка в карточке, вы сами предоставляете
доказательство против собственного кода.

Дальше: «медицинский пластик» у девяти таблетниц, «реабилитация» у двух массажёров,
«чехол» у пяти SKU.

Описания подождут. Срок 01.10.2026 — нет.

### Шаг 2. Заливка описаний

Для каждой группы:

1. Открыть файл группы в `descriptions/` — в начале таблица, какой текст какому SKU.
2. В кабинете выбрать категорию и **посмотреть счётчик над блоком «Описание»**.
   Единого лимита 5000 больше нет, он зависит от категории. Лимит ниже 1500 —
   резать блок «Уход», он последний по важности.
3. Скопировать текст. Заголовки блоков вставлять обычным текстом: разметку WB не держит.
4. Сверить наименование, предмет WB и описание — они должны говорить одно и то же.

Порядок: начинать с тех групп, где было хуже всего. Капы (479 знаков на восемь карточек),
эспандеры (один SKU на 464), таблетницы.

### Шаг 3. Характеристики — важнее описаний

`checklist-kabinet.md`, **раздел B**.

Основная масса ключей идёт в характеристики, а не в описание. Пустое поле прямо режет
ранжирование. У кап заполнено **одно** поле на восемь карточек — там заполнение полей
даст больше, чем любой переписанный текст.

Два правила WB, которые легко нарушить:

- Каждое значение — **отдельной строкой**, не через запятую, иначе товар не попадает
  в фильтры. Сейчас нарушено у `ACRB1MS101BL` и `ACRB1MS101PN`.
- «Назначение» — максимум 3 значения, «Комплектация» — максимум 12.

### Шаг 4. Ошибки в данных

**Раздел C**, 15 пунктов. Часть из них не про SEO, а про деньги: вес пробок 0,5 кг вместо
0,05 кг — это логистика на каждой отгрузке. «Вид грызуна» у товаров для собак уводит
карточки в чужие фильтры.

### Шаг 5. Проверка

Прогнать `scan-stop-words.sql` — **оба запроса**, второй по характеристикам.

Ожидаемо: ноль находок по риску R и A, кроме двух — «игрушка» в товарах для животных
и «в посудомоечной машине» в кухонных группах. Оба помечены 🟢 в словаре, это не ошибки.

Осталось что-то ещё — правка не долетела, разбирать по артикулу.

До заливки тот же прогон даёт 20 находок по характеристикам. Это точка отсчёта.

### Шаг 6. Вопросы поставщику

**Раздел D**, 12 пунктов. Ответы не блокируют заливку: в файлах помечено, что именно
удалить из текста, если факт не подтвердится.

Два стоят отдельно, потому что от них зависит код ТН ВЭД:

- **Консервный нож** — есть ли механический привод. Нет привода → код 8210 под вопросом.
- **Канаты** — 100 % хлопок или есть синтетическая сердцевина. Влияет на код 5609.

### Шаг 7. Частотность

Кабинет → Аналитика → Популярные запросы. Выгрузить и передать в следующую сессию.

Ядра во всех файлах собраны экспертно — из логики категории и текущих заголовков. Это
рабочая гипотеза, но гипотеза. С реальными частотами переставляются приоритеты, а где
разойдётся сильно — пересобираются наименования.

**Сделано частично 2026-08-23:** выгрузка по 60 SKU загружена, разбор — §7. По остальным
19 активным SKU ядра по-прежнему экспертные, выгрузка нужна.

### Сборка книги для заливки

Книга — то, что владелица открывает и переносит в кабинет:

| Скрипт | Что делает |
|---|---|
| `scripts/wb_after_upload_book.py` | сверяет витрину WB с книгой после заливки и собирает `Карточки_ВБ_после_заливки.xlsx`. Разбор — [`сверка-после-заливки.md`](сверка-после-заливки.md) |
| `scripts/build_cards_xlsx.py` | собирает книгу с нуля из `descriptions/*.md`: лист на группу, значения полей построчно внутри ячейки, подсветка расхождений с кабинетом |
| `scripts/apply_to_book.py` | вносит свежие значения **в книгу владелицы**, не стирая её оформление: ширины колонок, высоты строк, её цвета артикулов |
| `scripts/build_group_artifact.py` | сводный HTML на группу — заливка и инфографика в одном файле, `build/artifacts/<группа>.html` |

**В файл владелицы генератор не пишет.** У неё своя разметка и своя раскраска
(зелёным обработанные артикулы, красным снятые с продажи) — пересборка с нуля это
стирает. Поэтому в её книгу идёт только `apply_to_book.py` и только по названным
колонкам; расхождения показывает `--dry-run`, решение по ним за владелицей.

**Про сканер по характеристикам.** Первый запрос смотрит только наименование и описание.
Находки в полях характеристик он пропускает, хотя алгоритм площадки их видит,
а покупатель читает. Прогонять оба.

## 5. Три вещи, которые определяют всю логику

**Описание — не главное поле.** На Ozon оно вообще не участвует в текстовом поиске.
На WB индексируется, но весит меньше наименования и характеристик. Ключи распределяются
`наименование (ВЧ) → характеристики (основная масса) → описание (3–5 остаточных)`.
Описание пишется на конверсию, а процент выкупа весит в ранжировании больше, чем SEO.

**Формулировка не создаёт обязанность маркировки.** Обязанность возникает из кода
ТН ВЭД / ОКПД 2 и объективных характеристик товара. Но слово в карточке работает
по четырём каналам: как довод против собственного кода при споре о классификации,
как расхождение с декларацией соответствия, как заявление о лечебных свойствах без РУ
(ст. 24 ФЗ «О рекламе») и как сигнал алгоритму классифицировать карточку в чужую
категорию. Поэтому раздел A чеклиста идёт первым.

**Контекст решает, стоп-слово это или ключ.** «Массажёр» — риск для мячей, которые
уводят из 9019, и целевой ключ для группы ручных массажёров, где 9019 нужен.
«Игрушка» размывает предмет в спорттоварах и является предметом в товарах для животных.
Шкала риска в `stop-words.md` помечает такие случаи 🟢 с указанием группы — читать
пометку целиком, а не только цвет.

не попали — ядра по ним по-прежнему экспертные.

**Главное наблюдение: позиций нет ни у одного товара.** Колонка позиции пуста во всех
1 031 строке, кабинет по каждому товару пишет «В ТОП-100: 0%». Карточки не входят
даже в первую сотню ни по одному кластеру. Это согласуется с `WB_SKLADY_2026.md` §2:
71% товара заморожено на пострадавших складах, и WB перестаёт показывать карточку там,
где её нечем отгрузить. Пока не приедет поставка, **позиции — не мера качества текста**,
и правки описаний по ним оценивать нельзя.

**Покрытие текстом — то, что можно чинить сейчас.** Кластер считается покрытым, если
каждое его слово есть в наименовании, описании или характеристиках. По частотности
покрыто 86,5%, по числу кластеров — 687 из 1 031. Разрыв между этими двумя числами
и есть содержание работы: непокрытое — это в основном средне- и низкочастотный хвост,
но встречаются и жирные пропуски.

Самые дорогие непокрытые кластеры на срезе: «бокс для девушки» (17 463), «массажер
для рук» (15 237, 2 SKU), «тренажер для спины» (15 233, 3 SKU), «для кондитера»
(14 998), «шарик для массажа» (11 810), «мешок для стирки бюстгальтера» (11 298, 3 SKU).

Хуже всех покрыты массажные мячи: `ACRB1MS106BL` — 59,4% при 60 кластерах,
`ACRB1MS106RJ` — 57,7%. Там же и наибольшая частотность, так что начинать с них.

**Порядок работы с покрытием:**

1. `v_sku_keyword_coverage_summary` — отсортировать по `freq_total - freq_covered`,
   это очередь карточек.
2. `v_sku_keyword_coverage` по конкретному `nm_id` с `is_covered = false` — список
   кластеров, которых не хватает в тексте.
3. Ключи вносятся по правилу §5: ВЧ — в наименование, основная масса —
   в характеристики, 3–5 остаточных — в описание.
4. Перед внесением прогнать кандидата через `stop-words.md`: часть непокрытых
   кластеров непокрыта намеренно (уводят предмет в чужую категорию).

Пункт 4 не формальность. «Тренажер для спины» и «массажер для рук» у мячей — ровно
тот случай, когда ключ тянет карточку в 9019 и в обязанность маркировки (§5, раздел A
чеклиста). Частотность не повод вносить ключ.

## Почему «покрытие ключей» низкое, хотя описания залиты — разбор 18.09.2026

Вопрос владелицы: «я меняла их по файлу, который мы с тобой создали, вносила
изменения согласно ему. И теперь ты говоришь ключи не покрыты. Как так».

Разобрано до конца. Три причины, и первая снимает подозрение с заливки.

### 1. Залито верно

Текст в кабинете совпадает с файлом группы до буквы — сверено по
`ACRB1MS106BL` против `descriptions/myachi-106-107-109.md`. Заливка ни при
чём.

### 2. Что вообще меряет эта цифра

`freq_covered_pct` сравнивает текст карточки со списком **поисковых
запросов, которые WB сам привязал к этой карточке**. Не с нашим файлом
ключей, а с тем, по каким запросам площадка карточку показывает.

Запрос считается покрытым, только если **все** его слова буквально есть в
тексте. «Мячик массажный» не покрыт словом «мяч»: нужна форма «мячик».

Проверено: если считать по корням слов вместо точных форм, покрытие по
массажёрам поднимается с 50 % до 53,5 % — всего на 3,5 пункта. **Метрика
почти не врёт**, дело не в словоформах.

### 3. Стопроцентного покрытия не бывает, и добиваться его нельзя

Часть привязанных запросов товару не подходит. У массажных мячей среди
непокрытых: «тренажер для спины» (15 233), «мячик детский для малышей»
(6 355 — а «для малышей» вообще красное слово, его вписывать нельзя), у
эспандеров — «спорт товары» (6 220), «спортивный инвентарь для тренировок
дома» (1 705). Вписать их значит соврать в карточке ради показов.

Ориентир — не 100 %, а «закрыты все запросы, которые действительно про
наш товар».

### 4. Настоящая дыра всё-таки есть

Из 390 685 частотности по группе мячей 106 закрыто 109 425, то есть 28 % —
и это считая по всем четырём карточкам группы вместе, не по одной.

Крупнейшие незакрытые запросы, которые товару **подходят**:

| Запрос | Частотность |
|---|---|
| мячик массажный | 59 435 |
| мяч для пилатеса | 22 715 |
| массажер для рук | 15 237 |
| массажер для стоп | 8 732 |
| суджок-шарик | 8 302 |
| мячи для йоги | 7 573 |
| пилатес | 6 590 |
| теннисный мяч для массажа | 6 460 |

Вернуть их в тексты — это примерно +135 тысяч частотности, покрытие группы
выросло бы с 28 % до ~62 %.

### Почему они пропали

Описания писались с установкой «убрать воду»: длина 904-1181 знак вместо
ориентира 1 500-2 000, и это было согласованное решение. Вместе с водой из
текстов ушли синонимы — «мячик», «шарик», «су джок», «пилатес», «йога».
Слова остались в наименованиях соседних карточек группы, но каждая карточка
меряется отдельно, и соседям её показы не помогают.

**Это упущение при составлении файла, а не при заливке.** Когда группу будут
доделывать, синонимы нужно вернуть в текст - не россыпью, а внутри
предложений, которые и так описывают применение.
