# Vision — SellerBase как операционная система бизнеса маркетплейсов

> **Статус:** долгосрочная архитектурная визия. Не блокирует текущую разработку,
> но любой PR должен помнить: куда движемся.
> Источник: архитектурная сессия пользователя (док в Google Drive, июнь 2026).

---

## Куда мы идём

Проект перестал быть «WB-калькулятором акций». Формируется:

> **Операционная система управления бизнесом маркетплейсов**

Цель системы:
1. **Понимать бизнес** — а не просто показывать цифры
2. **Объяснять причины изменений** — почему просели продажи, почему растёт маржа
3. **Накапливать знания** — превращать наблюдения в правила и закономерности
4. **Предлагать решения** — рекомендовать действия с обоснованием
5. **Прогнозировать последствия** — симулировать «что если»
6. **Строить цифровой двойник бизнеса** — финальная цель

## Главная цепочка платформы

```
Данные
  → Наблюдение
  → Показатель
  → Факт
  → Состояние
  → Проблема
  → Расследование
  → Причина
  → Гипотеза
  → Проверка
  → Доказательство
  → Знание
  → Решение
  → Действие
  → Результат
  → Обучение
```

Каждое звено — отдельный слой системы. Сейчас мы покрываем только «Данные → Показатель».

## Главный объект и идентификатор

**Главный объект бизнеса** — **товар**. Не карточка, не заказ, не категория.

**Главный идентификатор** — **штрихкод**. Для текущей модели: `1 товар = 1 штрихкод`. Размеры/цвета/комплектации — отдельные товары.

В коде это уже отражено:
- URL карточки: `/products/[штрихкод]`
- Все таблицы кликают на штрихкод
- `sku_catalog.barcode` — единственный надёжный business identifier

---

## Ключевое изменение мышления

> **Архитектура больше не строится вокруг товара. Она строится вокруг покупателя.**

Новая цепочка:

```
Покупатель
  → Сценарий
  → Проблема покупателя
  → Причина покупки
  → Фактор выбора
  → Категория
  → Товар
  → Карточка
```

Это фундамент всех будущих модулей аналитики. Покупатель — главное действующее лицо.

В текущей сборке покупателя ещё нет как сущности. Это будет один из главных модулей следующего этапа.

## Архитектурные принципы (применяем сейчас и в будущем)

### 1. Хранить только факты, всё вычисляемое — на лету

**Не хранить как первичные данные:**
- CTR
- Конверсию
- Маржу
- Состояния товара
- Риски
- Возможности

Их вычислять. Уже соблюдается: в `entities/*/queries.ts` мы строим производные данные из фактов.

### 2. Версионность всего

Все основные объекты должны иметь историю:
- карточки
- знания
- решения
- категории
- контент
- цены
- тарифы

**Не хранить только текущее состояние.** Это обязательное требование для цифрового двойника.

Уже частично: `wb_stocks_history`, `cogs_history`. Не хватает: версионности карточек, решений, знаний.

### 3. Жизненные циклы (состояния) у всех ключевых объектов

Пример для товара:

```
NEW → GROWING → STABLE → DECLINING → CRITICAL → LEADER → ARCHIVED
```

Переходы вычисляются автоматически из фактов (продажи, выручка, маржа, тренд).

В UI это — цветной бейдж/чип на карточке товара. План: добавить вычисление состояния в `fetchCatalog`/`fetchProductDetailByBarcode` отдельным PR.

### 4. Промежуточные сущности, которых нет в типовых аналитиках

Эти концепции отличают нас от SellerStats / MP Profit:

- **Доверие** (от отзывов, рейтинга, истории магазина)
- **Видимость** (CTR, позиции в выдаче, реклама)
- **Воспринимаемая ценность** (цена vs ценность для покупателя)
- **Отклонение** (от плана, от нормы)
- **Причина покупки** (зачем человек берёт этот товар)
- **Фактор выбора** (что переключает между вариантами)
- **Решающий фактор** (что окончательно убеждает)

Примеры причинных цепочек, на которых будет строиться слой исследований:

```
Отзывы → Доверие → Конверсия → Продажи
Цена → Ценность → Конверсия → Продажи
Реклама → Видимость → CTR → Конверсия → Продажи
Контент → Покрытие факторов → CTR → Конверсия → Продажи
```

## Время и версионность

Все объекты должны иметь временную ось. Архитектурное требование:

> Не хранить только текущее состояние. Хранить версии.

Это обязательное требование для цифрового двойника.

---

## Что это значит для фронтенда (сейчас)

> **Не привязывать интерфейс жёстко к текущей структуре сущностей.**
> Высока вероятность появления новых объектов и связей.

Рекомендации, которые **уже соблюдаются**:

- **Модульный UI** — FSD-структура `app/widgets/features/entities/shared`
- **Конфигурируемая навигация** — `nav.ts` data-driven
- **Абстрактные карточки сущностей** — `CategoryCard`, `KpiCard`, `ProductTagBadge`, `StatList`
- **Универсальные таблицы и дашборды** — `DataTable<T>`, generic-обобщения везде

**Дополнительные правила** для будущих PR:
- Не вшивать жёсткие enum'ы — использовать конфиги
- Не делать «специальных» таблиц под одну сущность — переиспользовать `DataTable<T>` с разными колонками
- Новые сущности — в `entities/*` отдельной папкой
- Новые модули — в `features/*` без зависимостей от других features

## Текущий MVP в контексте визии

| Реализовано | Куда относится |
|---|---|
| `/dashboard` — KPI и тренды | Аналитический слой (показатели) |
| `/products` — каталог | Товарный слой |
| `/products/[id]` — карточка | Товарный слой |
| `/analytics` — ABC×XYZ | Аналитический слой (состояния товара частично) |
| `/pnl` — финансы | Аналитический слой |
| `/turnover` — оборачиваемость | Аналитический слой |
| `/sales-report` — pivot | Аналитический слой |
| `/deficit` — дефицит | Аналитический слой → переход к Расследованиям |
| `/reviews` — отзывы | Товарный слой (отзыв как сущность) |
| `/tariffs` — тарифы | Ограничения (тариф как ограничение бизнеса) |
| `/sources` — источники заказов | Аналитический слой (распределение) |
| `/ads` — реклама | Аналитический слой |

**Покрытие** визии: ~15-20%. Это «Данные → Показатель» — самое начало главной цепочки.

## Дорожная карта (ориентировочно)

### Ближайшее (1-2 месяца)

- Подключение реальных данных к оставшимся mock-модулям (Отзывы через WB Feedback API, Тарифы через WB API)
- Состояния товара (NEW/GROWING/STABLE/DECLINING/CRITICAL/LEADER/ARCHIVED)
- Аномалии и события (внезапные просадки, всплески)

### Средняя перспектива (3-6 месяцев)

- Слой Расследований: «почему просел этот товар?»
- Версионность карточек (история изменений названий/цен/описаний)
- Сущность Покупатель / Сценарий / Причина покупки

### Дальняя перспектива (год+)

- Слой Знаний: правила и закономерности
- Гипотезы и эксперименты
- Автоматизация (сигналы / прогнозы)
- Цифровой двойник
